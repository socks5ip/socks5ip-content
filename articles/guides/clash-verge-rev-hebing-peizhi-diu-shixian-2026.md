# Clash Verge Rev 里手加的线路，为什么订阅一更新就没了

把自己买的线路粘进「配置」页，隔天点一次更新，它们全没了——这不是 bug：整份文件被远程订阅换掉了。

**Clash Verge Rev 的远程订阅是「整文件替换」而不是「合并」：只要更新一次，你在订阅里手写的 proxies、proxy-groups、rules 都会被新文件覆盖。想让自制线路长期存在，只有两条路——写进「合并（Merge）」配置，或者放进 proxy-providers 单独维护。**

## 四个配置区，各自管什么

Verge 把配置分成了四类，很多人只在第一类里动手，所以每次更新都在重做同一件事。

| 类型 | 谁在用 | 会被订阅更新覆盖吗 | 适合放什么 |
|---|---|---|---|
| 远程订阅（Remote） | 平台或服务商下发 | 会，整份替换 | 什么都别手改 |
| 本地配置（Local） | 自己新建的空白配置 | 不会 | 完全自维护的一整套 |
| 合并（Merge） | 挂在一个订阅上生效 | 不会，独立文件 | 自己的 proxies 与 rules |
| 脚本（Script） | JS 处理器 | 不会 | 批量改字段、按条件删节点 |

判断你手上的配置属于哪一类很简单：点开文件看头部有没有订阅地址。有地址的就是远程订阅，对它做的所有手改都是临时的。

## 手改订阅为什么会丢：更新是替换，不是补丁

订阅更新的实现方式是「下载新文件 → 覆盖旧文件」，没有逐行比对这一步。你在本地加的三条线路，在新文件里不存在，覆盖时就一起没了。

这也解释了一个常见困惑：明明昨天还好的配置，今天打开看到的是别人的节点列表。不是你的改动没保存，是文件已经被换掉了。

## 做法一：把线路写进合并配置

合并配置是一个只写「要合并的键」的小文件，挂在订阅上生效，更新订阅不会动它。五个键覆盖了绝大多数需求。

| 键 | 作用 | 典型用途 |
|---|---|---|
| prepend-proxies | 插到 proxies 列表最前 | 自己的固定 IP，排最上面好找 |
| append-proxies | 追加到 proxies 列表末尾 | 自己的线路，不影响原有顺序 |
| prepend-rules | 插到 rules 最前 | 优先于订阅自带规则生效 |
| append-rules | 追加到 rules 之后 | 补充规则，但可能落在 MATCH 之后而失效 |
| append-proxy-groups | 追加策略组 | 把自己的 IP 做成一个可切换的组 |

写合并文件时只写这几个键，不要把整份配置复制进去：合并配置不是完整配置，塞进去的多余字段不会生效，反而让人误以为改成功了。

## 做法二：用 proxy-providers 单独管线路

如果自制线路会持续增删（比如按项目换 IP），更省事的是把它们做成一个独立的 provider 文件，再在配置里引用。这样线路维护与订阅维护彻底分开，更新订阅时完全不碰这一块。

provider 的好处是「一份线路文件，多处引用」：主配置、策略组、规则都可以指向同一个 provider，改一处就全局生效。代价是多一个文件要同步，换机器时需要一起搬。

## 三个高频坑

以下三种写法在社区里反复出现，共同点是「看起来成功、实际没生效」。

1. **把 Clash 订阅直接贴进合并配置。** 合并配置期望的是 `prepend-proxies` 这类键，塞一整份含 `proxies`、`rules`、`dns` 的配置进去，解析器只会挑它认识的部分，其余静默忽略。
2. **append-rules 排在 MATCH 之后。** Clash 的规则是从上往下命中即止，`MATCH` 是全量兜底；追加到它后面的规则永远不会被读到。
3. **改完不重启内核。** 只在界面点了保存，部分字段要重载内核才生效，表现就是「改了没反应」。

## 三步验证：改完怎么确认真的生效

不要靠「看起来在列表里」判断，跑完这三步才算改对。

1. **更新一次订阅**：在订阅上点更新，再看 proxies 列表里你的线路是否还在。还在，说明它已经不在被覆盖的那份文件里。
2. **切到合并配置看策略组**：如果线路进了策略组，在组里能选中它；选不中就说明键名或缩进有问题。
3. **跑一次实际请求看出口**：把流量指向你的线路，打开 [IP 综合检测中心](https://socks5ip.com.cn/ip-check-center/) 看出口属地是否等于那条线路的归属地。也可以先用 [代理线路检测](https://socks5ip.com.cn/proxy-check/) 确认握手通不通，再查出口。

第三步是唯一不会骗人的验证。前两步只能证明「配置被读进去了」，第三步才能证明「流量真的走了那条线」。

## 临界点：什么时候该换做法

判断标准不是线路数量，而是「你多久改一次」。

| 你的情况 | 该用哪种 |
|---|---|
| 只加两三条固定线路，长期不动 | 合并配置，一次写完不用管 |
| 线路按项目轮换、经常增删 | proxy-providers，独立文件维护 |
| 想整份自己控制，不要订阅 | 本地配置，从空白开始 |
| 需要在更新时自动删掉某些节点 | 脚本（Script），按条件处理 |

还有一个容易被忽略的临界点：如果你同时用多个订阅，合并配置要分别挂在每个订阅上，否则切订阅就失效。

## 常见问题

**Q：Clash Verge Rev 里改了配置，更新订阅后全没了，正常吗？**
正常。远程订阅更新是整份替换，手改的内容不在新文件里就会被覆盖。要长期保留就写进合并配置或 proxy-providers。

**Q：合并配置和本地配置有什么区别？**
合并配置挂在订阅上生效，只写要追加的部分，更新订阅不影响它；本地配置是一份独立的完整配置，不与订阅关联，全部自己维护。

**Q：prepend-proxies 和 append-proxies 该用哪个？**
只影响顺序，不影响能否生效。想让自己买的线路排在列表最前面、方便找就用 prepend，不想打乱原有顺序就用 append。

**Q：为什么我加的分流规则一条都没生效？**
先看规则是不是追加在 MATCH 之后。Clash 从上往下匹配、命中即止，MATCH 是全量兜底，放在它后面的规则读不到。

**Q：合并配置里能不能直接写一份完整的 Clash 配置？**
不建议。合并配置只识别 prepend/append 这类键，塞整份配置进去会有大量字段被静默忽略，排查起来很费时间。

**Q：多台设备怎么同步这些自制线路？**
把线路写进 proxy-providers 的独立文件，再把该文件放进同步目录或自建链接；合并配置跟着订阅走，不需要逐台重写。
