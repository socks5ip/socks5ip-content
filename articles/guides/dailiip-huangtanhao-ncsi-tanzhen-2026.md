# 黄叹号亮着网页照样开：Windows 判联网靠的是一行 txt

右下角那个黄叹号从来不是「网断了」的意思，它只说明一件事：系统去取一行固定文本，没取回来。

挂上代理之后图标变黄、浏览器里 https 站照开，这种组合完全成立。Windows 判断「有没有网」走的是一条 HTTP 探测请求，取回 www.msftconnecttest.com 下的 connecttest.txt，正文必须是 `Microsoft Connect Test` 这 20 个字符，多一个少一个都判失败。本机五次复跑的中位数是：直连 **413 毫秒**、经本地 SOCKS5 **184 毫秒**，两次都是 **200**，内容一字不差——代理既不改写也不拦截这条请求，它只影响这条请求能不能被送出去。

| 你看到的 | 它实际在说 | 本机实测对应 |
|---|---|---|
| 黄叹号，网页能开 | 探针没拿到那行文本 | 探测域名被分流规则漏到直连一侧 |
| 黄叹号，网页也打不开 | 两条探测都没过 | DNS 探针同时失败 |
| 图标正常，程序不通 | 探针走直连，业务走代理 | 探针 200，业务出口没换 |
| 地球仪、提示需登录 | 探针被劫持到认证页 | 返回 HTML 而不是 txt |

数据来源：全网低价IP 实测（Windows 11 本机 NCSI 探针复跑 5 次取中位，2026-11-28）。

## 它取的是文本，不是速度

这套判定既不测带宽，也不 ping 任何地址，只做一件事：按注册表里写死的地址去要一个文件，比对内容。三个键分别回答去哪取、取哪个路径、内容该是什么，改一个字就判失败。

| 键 | 本机值 | 管什么 |
|---|---|---|
| ActiveWebProbeHost | www.msftconnecttest.com | HTTP 探针打哪个域名 |
| ActiveWebProbePath | connecttest.txt | 取哪个文件 |
| ActiveWebProbeContent | Microsoft Connect Test | 正文必须等于这串字符 |
| ActiveDnsProbeHost | dns.msftncsi.com | DNS 探针查哪个名字 |
| ActiveDnsProbeContent | 131.107.255.255 | 解析结果必须是这个地址 |

两条探针只要有一条通过就判定联网，所以只有 IPv6 出口的机器上，v4 探针失败同样不该被当成断网。本机的 ipv6.msftconnecttest.com 五次全部解析失败，图标却一直正常，原因就在这里。

## 35 秒是它愿意等你的上限

单次探测最多等 35 秒就判死，没有活动时每 15 秒重探一次，三个数字都在同一处注册表里，单位全是秒。把它们换成十六进制读会看错，`0x23` 是 35 不是 23。

| 键 | 十六进制 | 实际值 | 行为 |
|---|---|---|---|
| WebTimeout | 0x23 | 35 秒 | 单次探测等多久算失败 |
| PassivePollPeriod | 0xf | 15 秒 | 空闲时多久重探一次 |
| StaleThreshold | 0x1e | 30 秒 | 多久没结果就把状态标成过期 |

这两个数字解释了两个常见的时间感。一是「挂上代理过半分钟才变黄」：探测不是即时的，最长要等 35 秒，加上 15 秒的轮询间隔，从点连接到图标翻脸刚好落在这一段。二是「拔网线不会立刻变红叉」：红叉来自网卡层，几乎是瞬时的；黄叹号来自探测层，得等这一轮跑完。

## 代理不是凶手，是请求没送到

同一个探测地址直连 200、经 SOCKS5 也 200，说明转发这个动作没问题。真正让图标翻脸的是这条请求压根没走到代理手上，四个漏点按出现频率排：分流规则没覆盖探测域名（这类名字既不像国内也不在规则表里，容易被划到直连）、客户端只接管了指定程序（系统级探测不在名单里）、TUN 与系统代理同时开（一个改路由一个改应用层设置，打架时探测走了一条已不存在的路）、客户端崩了没还原系统代理（探测打到没人监听的本地端口）。

四种漏点有同一个验证方法，比换线路有用得多：把探测地址原样请求一遍，看返回的是 200、407、连接被拒还是超时。200 但内容不对，是中间有人改写（认证页、企业网关）；407 是代理要凭据而系统代理那条路给不出来；连接被拒基本是本地端口没人听；超时才说明真出不去。

## 四种图标对应四个故障层

认错层比不排查更费时间——把黄叹号当线路故障去换线，换完还是黄叹号，因为换的是业务出口，探测请求根本没走那条路。

| 图标 | 先做哪一步 | 最可能的成因 |
|---|---|---|
| 黄叹号 | 手工请求一次那行 txt，看状态码 | 分流漏掉探测域名、DNS 解析不到、出口侧掐 80 端口 |
| 红叉 | 看网卡状态，退出所有代理客户端 | 网卡禁用、驱动异常、虚拟网卡抢路由 |
| 地球仪 | 先在浏览器里把认证页走完 | 酒店、机场、校园网、企业网关的强制门户 |
| 图标正常但程序不通 | 查业务程序的出口 IP | 只接管了部分程序，或代理端口本身不通 |

第四行是反向的错觉：图标全绿不代表业务通。TUN 没开、系统代理没生效、程序自己忽略环境变量，这几种情况下探测走直连照常通过，业务却直连出去了，出口没换、账号还在原地。

## 自测口径：三条命令定性

| 步骤 | 做什么 | 判据 |
|---|---|---|
| 1 | 浏览器打开任意 https 站 | 能开 → 业务链路正常，问题只在指示器 |
| 2 | curl -i http://www.msftconnecttest.com/connecttest.txt | 200 且正文是那行文本 → 探针本该通过 |
| 3 | curl -x socks5h://127.0.0.1:端口 -i 同一地址 | 也 200 → 代理无罪；不通 → 查端口与规则 |
| 4 | Test-NetConnection 127.0.0.1 -Port 端口 | TcpTestSucceeded 为假 → 客户端没在监听 |

第二步和第三步的差别是关键：第二步走系统当前路径（可能直连、可能被 PAC 分流），第三步强制走代理。两步都 200 说明两条路都通，黄叹号是客户端改系统代理后没把探测请求一起接管造成的；只有第三步 200 说明直连那条路断了，探针走的正是断掉的那条；两步都不通，才轮到查 DNS 和线路。

跑之前记得清掉 http_proxy 这类环境变量，否则 curl 默认会读它们，第二步其实已经走了代理，两步变成同一步，结论自然错。

## 无人值守的机器，别拿图标当判据

多开机器上最贵的不是修一次，而是系统自己判成断网之后，把整套流程连同排队任务一起停了。脚本里写 ping 8.8.8.8 不通就重启代理，这条判据在三种情况下都给错答案：目标站封 ICMP 时它报不通但业务全好、代理只转 TCP 时它压根没经过代理、出口侧掐 ICMP 却放行 443 时它把好线判成坏线。

换成 HTTP 请求并检查内容，误判率立刻下来。一套够用的探活分四层，从便宜到贵依次跑，前一层过了就不跑后一层：进程在不在、端口通不通、真实握手成不成功、业务请求有没有拿到预期响应。第三层最关键——端口开放但握手失败的线路很常见，只有按 RFC 1928 做真握手才区分得出来。

探针本身很轻，一条几元档的线路跑几十次探测毫无压力，真正吃额度的是业务连接数。别为了省探针把间隔从 15 秒拉到 5 分钟，那样故障发现时间也跟着涨 20 倍。

## 常见问题

**Q：黄叹号出现但网页能开，要不要处理？**
A：不影响使用，可以先不管。它是本地指示器没拿到那行探测文本，业务流量走的是另一条路。想让它恢复，把探测域名放行进代理规则，或者保证直连那一路的 DNS 可用。

**Q：开了代理还是本地 IP，跟这个探针有关吗？**
A：无关，但会被它掩盖。图标全绿可能是探针走了直连，业务却直连出去了；判断方法是打开 IP 综合检测中心看出口，业务程序看到的 IP 和后台显示的出口对不上，就是没接管。

**Q：把 EnableActiveProbing 关掉行不行？**
A：能关，代价比图标大。应用商店下载队列、系统更新检查、部分邮件客户端的收信策略都读这个联网状态，一起被关进「无网」模式之后，会出现一批很难联想到注册表的异常。默认值是 1，改之前先记原值。

**Q：为什么有的机器一挂代理就变成地球仪、提示需要登录？**
A：探测请求被网关或代理劫持到了认证页，返回的是 HTML，和注册表里那行文本对不上。先过掉认证页再挂代理，顺序别反。

**Q：手机连 Wi-Fi 提示无法访问互联网，但微信能用？**
A：同一个机制。手机探针没拿到预期内容就会这样提示，甚至自动切回移动数据。微信能通说明链路是好的，多半是探针域名被拦或 DNS 没解析对，与代理配置无关。
