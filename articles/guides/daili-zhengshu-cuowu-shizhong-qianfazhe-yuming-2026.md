# 浏览器报证书错误：先对时间，再看签发者，最后查域名

打开一个两小时前刚换过证书的站点，浏览器先弹出一块红色警告，正文写着「您的时钟快了」。换一条线路、换一个出口，警告一字不差。

原因很直接：**证书只校验三样东西——有效期、签发者、域名，这三样都在你和网站之间的 TLS 握手里确定，跟出口 IP 是哪家的、在哪个国家没有关系。** 代理在传输层搬字节，它连证书长什么样都不知道。

| 浏览器提示 | 校验项 | 真因落点 | 换 IP 有用吗 |
|---|---|---|---|
| 时钟不准 / 证书已过期 | 有效期 | 本机时钟偏差，双系统常差 8 小时 | 没用 |
| 证书不受信任 | 签发者 | 安全软件、企业网关、公共 Wi-Fi 认证页 | 没用 |
| 名称不匹配 | 域名（SAN） | hosts、域名解析被改、直接用 IP 访问 | 偶尔间接有用 |

数据来源：RFC 5280 §4.1.2.5 / RFC 8446 §4.4.2.4 与 Chromium 证书错误码对照（2026-11-22 复核）

## 代理为什么改不了证书

**SOCKS5 按 RFC 1928 只做一件事：把「谁要连哪个地址的哪个端口」办成，办成之后退到一边搬数据。**

客户端发 CONNECT 命令，里面只有目标地址类型、目标地址、目标端口三段；服务端回一个成功应答码，从那一刻起这就是一根透明管子，两端传什么它原样递过去。你的 TLS 握手报文（ClientHello、证书、Finished）对它来说只是一串字节，它既不解析也无法替换。

HTTP 代理走另一条路，结论一样。RFC 9110 §9.3.6 定义的 CONNECT 方法先开一条隧道，隧道建好后代理只剩双向复制，TLS 在隧道内部端到端完成。L2TP 更靠下，RFC 2661 建的是二层隧道，连 IP 层都封在里面运。

唯一的例外是有人在本地装了根证书、把 TLS 终结后重新签一张，业内叫中间人解密。这时候证书确实变了，但变的不是转发行为，是有人主动拆了信封再封上——正规卖出口的平台不做这件事。

## 三条文案，各指一层

**ERR_CERT_DATE_INVALID 说的是有效期，ERR_CERT_AUTHORITY_INVALID 说的是签发者，ERR_CERT_COMMON_NAME_INVALID 说的是域名。文案已经把答案写在脸上了。**

第一类比对的是证书里 notBefore 与 notAfter 两个时间戳（RFC 5280 §4.1.2.5 的 validity 字段），参照物是本机时间。看到它就去对表，不要动网络。

第二类往上追签发者是否在系统信任库里，追不到可信根就报。它常被误读成「证书是假的」，其实证书可能完全合法，只是签它的根你这台机器不认。

第三类把证书 SAN 列表里登记的域名和地址栏里敲的域名做比对，对不上就报。Firefox 把三条换成 SEC_ERROR_EXPIRED_CERTIFICATE、SEC_ERROR_UNKNOWN_ISSUER、SSL_ERROR_BAD_CERT_DOMAIN，一一对应，判断方法一样。

还有一种「看起来像证书错误」的：页面直接跳到要求输手机号或点同意的登录页。那不是校验失败，是网络层做了重定向，公共 Wi-Fi 的认证页最常这么干。

## 临界点：8 小时的偏差为什么只卡住少数站

**常见证书有效期是 90 天甚至 1 年，8 小时的偏差落在有效区间内，校验照样通过；只有刚签发不到 8 小时的新证书、或刚过期几小时的旧证书会被这条偏差卡住。**

所以症状常常是「大部分站正常，只有某几个站报时间错」。看到这个形态，先别怀疑站，先对表。

偏差从哪来，最典型的是双系统。Windows 默认把主板 RTC 当本地时间读，Linux 默认当 UTC 读，同一块电池供出来的时间在两个系统里差整整 8 小时。切回 Windows 打开浏览器，新签发的证书立刻被判成「尚未生效」；反过来切到 Linux，可能变成「已过期」。

第二种是老机器和虚拟机的时钟漂移：主板电池没电的笔记本每次开机回到出厂年份，虚拟机从快照恢复时时钟停在快照那一刻，笔记本合盖几天再开有时不会立刻同步。这三种都不报网络错，只在打开 https 站时才暴露。

## 自测口径：三条命令加一次对表

**Windows 用 `w32tm /query /status` 看时间源与偏移、`w32tm /resync` 强制同步；macOS 与 Linux 用 `date -u` 看 UTC，配合 `timedatectl` 确认 NTP 在跑。**

对表还有个更笨但更快的办法：跟手机时间比一眼。手机时间基本都准，误差超过两分钟就值得处理。

时间这项过了还不正常，再查签发者。点开警告详情里的「证书」一栏，看签发者那行的名字：写着公共 CA 的名字就正常，写着公司名、安全软件名或陌生字符串，说明链路上有个设备终结了 TLS 再重签——企业网关的 SSL 检查、安全软件的网页防护都会这么干。

最后才查域名。用 IP 直接访问、hosts 里写了固定解析、或者本地 DNS 被改，都会让 SAN 比对失败，这三种换线路一样报错。

## 常见问题

**问：挂上代理就报证书错误，换一条更贵的线有用吗？**
答：基本没用。证书三项都在端到端握手里确定，换出口不改变任何一项。只有「名称不匹配」这一类偶尔间接有效——那是解析被改了，换线可能顺带换了出口的解析路径。

**问：为什么只有某几个网站报时间错，其他都正常？**
答：因为偏差只有 8 小时，落在常规证书的有效区间内。只有刚签发或刚过期的证书才会被这条偏差卡住。

**问：提示「证书不受信任」，是不是网站有问题？**
答：先看你机器里多不多一张根证书。企业网关做 SSL 检查、安全软件做网页防护，都会下发自己的根证书，签发者就变成公司名。这类是善意中间人，但如果你没装过任何东西，就要警惕。

**问：直接填 IP 访问为什么报名称不匹配？**
答：证书 SAN 里登记的是域名，不包含那个 IP，比对必然失败。要测线路就用检测页，不要用 https 直接敲 IP。

**问：控制台报错但页面能打开，算不算证书问题？**
答：不算。能打开说明校验过了，控制台那行多半是某个子资源（图片、接口）的证书链有问题，查那一个域名即可。
