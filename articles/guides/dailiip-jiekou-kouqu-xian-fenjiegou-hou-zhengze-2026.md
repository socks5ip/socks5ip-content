# 从接口和网页源码里批量抠代理：先切结构，再谈正则（2026）

一整段接口返回粘进提取框，多数人的第一个动作是写正则；更省事的顺序是先看清这段东西的结构——字段在哪一层、IP 和端口是不是被标签隔开，结构清楚了，规则往往只剩一条。

**一句话结论：**批量抠代理的**顺序比正则本身更重要**：**先按来源把文本切成「一条一条」，再在单条里取字段，最后统一成「IP:端口:账号:密码」或代理链接**。三种来源的脏法完全不同——**接口 JSON 是键名不统一**（`ip`／`host`／`server` 都有人用）、**网页源码是标签隔断**（`<td>1.2.3.4</td><td>8080</td>`）、**日志是伪 IP 干扰**（时间戳、版本号长得像地址）；按这个顺序处理，比逐条写正则少一半返工。

## 一、三种来源，三种脏法

先认清自己手上是哪种文本，再决定用工具还是用正则。三种来源的失败原因完全不同。

| 来源 | 典型样子 | 真正的坑 | 该先做什么 |
|---|---|---|---|
| 接口返回 JSON | `{"data":[{"ip":"1.2.3.4","port":8080}]}` | 键名各家不同，`ip` 可能是 `host`／`server`／`addr` | 先按 JSON 解析，取数组再逐条读字段 |
| 网页源码 | `<td>1.2.3.4</td><td>8080</td>` | IP 与端口被标签隔开，正则跨不过标签 | 先剥标签转成纯文本，再按行切 |
| 运行日志、聊天记录 | `[12:03] connect 1.2.3.4:8080 ok` | 时间戳、版本号、端口号混在一起 | 先按「四段数字」形态粗筛，再校验每段范围 |

三种里最容易翻车的是第三种：`12:03` 和 `1.2.3.4` 都是数字加点，纯正则一锅端会把时间戳当 IP 抓出来。

## 二、先切结构：一步把「一大坨」变成「一行一条」

粘进提取工具之后，第一步选的不是输出格式，而是切分方式。多数提取工具支持按换行、按分隔符、按「IP:端口」形态三种切法。

1. **能按结构切就别按形态切。** JSON 先取数组，HTML 先剥标签，这样每条记录天然对齐。
2. **剥完标签再压空白。** `<td>` 之间常有换行和缩进，直接按行切会切出一堆空白行。
3. **一行只留一条记录。** 有的一条里塞了四段（IP、端口、账号、密码），有的只塞两段；先统一成一行一条，后面取字段才不会串行。

这一步做完，肉眼就能看出总共多少条、有没有明显残缺的。

## 三、输出形态选哪个，看下一步去哪

提取完的下一步决定输出格式。选错不会报错，但会在下一个环节静默失败。

| 输出格式 | 适合喂给 | 注意 |
|---|---|---|
| `IP:端口` | 测活脚本、客户端单条添加 | 无认证的线路才成立 |
| `IP:端口:账号:密码` | 有认证的线路、批量导入 | 四段顺序各家不同，导入前对一次示例 |
| `socks5://IP:端口` | Clash、NekoBox 这类客户端 | 协议头写错会整段导入失败 |
| 只要 IP | 查归属地、统计去重 | 后续要按 IP 反查平台时用 |

批量导入最容易错在第三行：协议头有 socks5、http、https 三种，各对应一种协议，客户端按头识别。填错头不会提示，只会显示「节点无效」。

## 四、私有地址必须剔掉，否则测活全是红的

提取结果里常年混着 `10.x`、`172.16–31.x`、`192.168.x`、`127.x` 这几段。它们看着像 IP，实际是内网地址，任何公网检测都连不上。

| 段 | 性质 | 处理 |
|---|---|---|
| `10.0.0.0/8` | 私有 | 剔除 |
| `172.16.0.0/12` | 私有 | 剔除 |
| `192.168.0.0/16` | 私有 | 剔除 |
| `127.0.0.0/8` | 环回 | 剔除 |
| `100.64.0.0/10` | 运营商级 NAT | 视用途，一般剔除 |

剔完再看条数。一批里如果三成是私有段，说明源头把内网配置也一起导出来了，回去改导出范围比在结果里筛更快。

## 五、抠完先测活，别直接进业务

提取只解决了「格式对不对」，没解决「能不能用」。中间必须插一步可用性检测，否则错误会延迟到业务侧才暴露。

- **先小批测活。** 抽十条跑一次线路可用性检测，看真实协议握手是否成功；只看端口通不通会漏掉协议不对的线。
- **再看出口归属。** 用 IP 综合检测中心看出口地址与归属地，和卖家标的地区对不上就先别用。
- **最后才批量导入。** 测活通过的再导进客户端，失败的回源头查导出条件。

这一步的顺序不能倒：先导入再测活，失败记录会和正常记录混在一起，事后分不清是线路问题还是导入问题。

## 常见问题（FAQ）

### Q：接口返回的 JSON 里键名不一样，怎么批量处理？

先打印一条完整记录看键名，再按实际键名取字段。常见的是 `ip`／`host`／`server` 三种，端口可能是 `port` 也可能是数字或字符串，取之前统一转成字符串，避免拼接时报类型错误。

### Q：正则抓出来的 IP 里混着时间戳和版本号怎么办？

按段校验：四段数字每段要在 0 到 255 之间，且不能是私有段。版本号常带三段（如 `1.2.3`），时间戳带冒号，这两类会被范围校验先刷掉。

### Q：提取出来的格式带协议头，能直接导入吗？

能，但要确认协议头和线路实际协议一致。`socks5://` 的头配 L2TP 的线路必然失败，客户端只会提示节点无效，不会告诉你是头写错了。不确定就先去掉头，按「IP:端口:账号:密码」导入。

### Q：为什么提取出来一批，测活一半以上是红的？

三种常见原因：混进了内网地址、账号密码顺序错位、线路本身已过期。先剔私有段，再核对一条成功记录的字段顺序，最后才怀疑线路。

### Q：多少条一批比较合适？

单批建议不超过两百条。批量检测对每条都要建连接，条数太多会拖慢且容易被目标侧限速；分批跑，失败记录单独存一份再复查。
