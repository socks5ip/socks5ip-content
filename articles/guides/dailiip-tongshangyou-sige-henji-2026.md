# 两家代理IP 段挨着？四个痕迹判同上游（2026）

一次尽调的账很好算：两家各买一个最小档，加起来通常不到十元，换到的是一张能逐条对账的表，而不是"感觉像是同一家"。价格、宣传页、平台数量都不参与判断，能用的只有四个技术痕迹。

**判断两家是不是同一个上游，看四个痕迹：抽 8 到 10 条 IP 比前三段（≥3 条同 /24 即高度可疑）、反查 PTR 后缀模板、比对提取接口的字段与报错原文、看协议与端口组合有没有一起"遗传"。对上三个基本可以按同一上游对待，只对上一条先别下结论。**

## 一、分销层级决定了为什么会有同段

地址不是一条一条卖到你手上的：区域注册机构按块分配，最小常见单位是 /24（256 个地址），这一段先给到 ISP 或机房，再整段转租给上游池，上游按条分销给各家平台。平台可以自营前台，也可以直接贴牌。

| 供应层级 | 谁在卖 | 数据面特征 | 价格形态 |
|---|---|---|---|
| 自营家宽池 | 自己持线路、自己养设备 | 段分散、PTR 命名自定义、换线节奏稳 | 档位少、单价偏高 |
| 一手代理 | 有独立后台与工单体系 | 段随上游、接口字段统一、有开放文档 | 中位，靠量谈折扣 |
| 二级分销／贴牌 | 只有前台页面与收款 | 与上游几乎一致，只换品牌与客服 | 低，靠加价率吃饭 |

这张表解释了为什么"便宜"不能当判据：一手代理做活动时能压到比贴牌更低，自营池也可能因为档位少而显得贵。价格只反映渠道策略，不反映货源位置。

## 二、第一处痕迹：八条样本的前三段

从两家后台各提 8 到 10 条，只比前三段。同一个 /24 通常属于同一个持有者，正常情况下不会无缘无故被两家独立渠道各切一半卖。

| 重合条数（8 条样本内） | 判读 | 下一步 |
|---|---|---|
| 0 条 | 不能判同源，也不能判不同源 | 继续查 PTR 与控制面 |
| 1-2 条 | 可疑，可能是同城同 ISP 的自然连号 | 换时间再抽一轮，看是否复现 |
| ≥3 条 | 高度可疑同一池子 | 查 PTR 后缀是否同模板 |
| 8 条全同段 | 确定同段，但还不能确定同一卖家 | 按"同段"采购，别按"同平台"采购 |

线画在 3 条的理由：跨省、跨运营商的池子里，随机抽 8 条出现 3 条同 /24 的概率极低；而同一 /24 内连号属于地址分配的正常形态，1 到 2 条只算疑点。单条撞段没有判读价值。

## 三、第二处痕迹：反向解析里的持有方签名

正向解析归域名主人管，反向解析（in-addr.arpa）归地址持有方管，所以 PTR 记录实际写着"这段地址是谁家的、什么类型"。平台换个招牌，改不掉它。

| PTR 形态 | 说明 | 采购含义 |
|---|---|---|
| …dynamic…pppoe…broadband… | 运营商动态家宽段 | 住宅出身，换线频繁属正常 |
| …static…ftth… | 静态家宽或专线 | 稳定性较好，段可能被多次转租 |
| …cloud…compute… 或机房缩写 | 云厂商／IDC 段 | 名义住宅实际托管的常见组合 |
| 无 PTR 记录 | 持有方没配反向 | 不能当"脏"的证据，只能当缺线索 |

查法三条任选：nslookup、dig -x、PowerShell 里 Resolve-DnsName 加 -Type PTR。关键在于比对模板：两家的后缀如果连分隔符习惯都一样，基本是同一个持有方在维护反向区。但 PTR 相同也不等于同一个卖家——同一家 ISP 的家宽段本来就是一个模板，这一条必须和 /24 一起看。

## 四、第三处痕迹：后台字段比线路更难改

真正难改的是后台，不是线路。数据面（IP、带宽、延迟）上游给什么就是什么，但控制面是上游写的代码，换品牌的人通常只改 Logo 和域名。

| 控制面痕迹 | 看什么 | 同源的信号 |
|---|---|---|
| 返回结构 | 字段名与层级，如 code/msg/data | 命名习惯完全一致 |
| 错误文案 | 余额不足、白名单未加、提取过快时的提示原文 | 连标点与括号都相同 |
| 限频规则 | 几秒一次、超了返回什么 | 间隔数字与惩罚方式相同 |
| 换线冷却 | 切换后多久可用、失败是否计次 | 冷却时长精确到同一数值 |
| 区／线路命名 | "一区、二区"或"A/B/C 档"的叫法与排序 | 命名体系与顺序一致 |

这条最准，也最容易被忽略：多数人只比价格，不比接口。要注意一个假阳性——同一个 SaaS 服务商给多家做白牌后台时，字段也会像，所以看到"接口一模一样"之后，还要回到 /24 与 PTR 上确认是不是同一批地址。

## 五、第四处痕迹：不支持的功能会一起继承

上游只开什么协议、只给哪段端口，下游通常一模一样，连不支持的功能也会一起继承。加一个 HTTP CONNECT 或 UDP 转发都要在后端开口子，前台加不出来。

四个可查的遗传特征：只给 SOCKS5 不给 HTTP 代理；端口集中在某一段（常见一万到两万之间的连号）；不支持 UDP ASSOCIATE，游戏语音和部分实时业务走不通；L2TP 档单独计费且换线慢，说明背后是独立设备资源。

验证一条线支持什么，一条命令够用：curl 加 -x socks5h://用户:密码@IP:端口 跑一次握手，再换成 -x http:// 跑一次，不支持 CONNECT 的会直接报错。两家的"不支持清单"完全重合，比"支持清单"更能说明同源——支持是宣传点，不支持是没人愿意改的坑。

## 六、自测口径：半小时做出一张对账表

| 步骤 | 动作 | 记什么 |
|---|---|---|
| 1 | 两家各买最小档，别买年付 | 下单时间、实付金额 |
| 2 | 各提 8-10 条，同一时间段提 | 完整 IP、提取时间 |
| 3 | 算前三段与 ASN | /24 列表、ASN 号 |
| 4 | 反查 PTR，跑一遍协议测试 | PTR 后缀模板、支持/不支持清单 |
| 5 | 打开两家的提取接口文档 | 字段名、报错原文、限频数字 |

五步加起来半小时内能做完。有一条边界要说清：这套方法查不出池子多大、是不是真独享、明天会不会停服。同源本身不丢人，问题在于同一段被两家同时零售——你在 A 家买的 IP，可能已被 B 家客户用过。

降低风险的动作只有一个方向：**按段分散，不按平台分散**。两家买的 20 条如果全落在 3 个 /24 里，实际分散度和在一家买 20 条差不多；一家能不能给你跨 5 个以上 /24、跨 2 个以上 ASN，比它叫什么名字重要得多。

## 八、常见问题

**Q：两家平台的 IP 段挨着，是不是同一家？**
A：只能说高度可疑。先抽 8-10 条算 /24 重合率，≥3 条同段再查 PTR 后缀模板；两条都对上，才按同一上游对待。

**Q：ASN 相同就代表同源吗？**
A：不代表。ASN 只说明这段地址由同一个网络运营方宣告，家宽池整段转租给多家上游是常态。离"同一个卖家"还差两层。

**Q：怎么确认买到的"独享"是真独享？**
A：技术痕迹查不出来。可行的是长期观察：同一条线连续几天在同一目标站的行为是否稳定、同 /24 内有没有别的活跃地址。

**Q：同源会不会更容易被目标站关联？**
A：会，但决定因素是同 /24 的条数，不是平台数量。20 条落在 3 个 /24 里，无论来自几家平台，风险一样高。

**Q：换一家平台就能避开同一批 IP 吗？**
A：不一定，反而可能买到同一段。想避开就按段选：先提 8 条看前三段，段与你手上重合的直接放弃。

**Q：不会查 /24 和 PTR，有更省事的办法吗？**
A：先用检测工具把 IP 的归属、类型、ASN 拉出来，再对两组结果比一遍。地址干净不等于线路能用，检测之后仍要跑一次真实业务。
