# 为什么浏览器显示代理生效，业务程序却还是本地出口

客户端显示已连接，浏览器也能打开代理地区的页面，可真正跑业务的那个程序，出口还是本地 IP。这两件事从来不是一回事。

状态灯亮只说明客户端与代理服务器之间建好了一条连接。跟你机器上其他程序有没有把流量交给它，是两条独立的链路。

**验证只看四个字段：源地址是不是本机或回环、目标地址是不是你买的代理服务器、目标端口是不是后台给的那一个、TLS 握手里的域名有没有露出来——四项都对，才算真的走了代理。**

| 接管方式 | 谁会跟着走 | 抓包看哪里 | 漏掉的样子 |
|---|---|---|---|
| 系统代理（WinINET / 系统设置） | 浏览器、部分桌面软件 | 回环口上的明文请求 | 网卡上出现直连真实站点的包 |
| 应用内代理（软件自己填） | 只有这一个软件 | 回环口 + 该进程出站 | 同机其它软件完全没走 |
| 虚拟网卡 / TUN 全局 | 整机（回环与本机网段除外） | 虚拟网卡的出站方向 | 残留路由导致部分网段绕过 |

## 绿灯只证明客户端自己连上了

接管方式不同，覆盖面差得很远：系统代理写的是注册表那一栏，认这一栏的软件跟着走，不认的一个字节都不走；应用内代理更窄，只影响填了地址端口的那一个程序；虚拟网卡才是整机接管，它把默认路由指向自己。

「网页能打开」这条证据几乎不值钱——浏览器恰好是最认系统代理的那一类软件，它通了，只能证明浏览器通了。

| 你看到的 | 它真正代表的 | 接下来该做什么 |
|---|---|---|
| 客户端显示已连接 | 客户端到代理这一段通了 | 去看别的程序的包 |
| 浏览器打开是代理地区语言 | 浏览器走了代理 | 验你真正跑业务的程序 |
| 业务程序跑完没报错 | 只证明连上了目标站 | 对照出口 IP，或抓这个进程的包 |
| 抓包里全是直连真实站点的包 | 这个程序没走代理 | 换接管方式，或单独给它配代理 |

## 三个抓包点，结论会相反

回环口能看到客户端与代理之间的明文握手，物理网卡能看到谁在绕过代理直连，上游网关只能看到加密后的流量。

第一个点是回环。代理客户端通常在本机开一个监听端口，业务程序连的是这个本地端口，这段流量压根不出物理网卡。Linux 上 `tcpdump -i lo port 1080` 就能看到；Windows 上 Wireshark 要在装 Npcap 时勾上回环适配器，否则网卡列表里根本没有这一项，界面还不会提示你少了什么。

第二个点是物理网卡。这里出现的东西多半是「没走代理」的证据：目标地址是真实站点、端口是 80 或 443，说明有程序绕过了客户端直连。整机接管的情况下，这里应该只剩到代理服务器的流量。

第三个点是上游网关。多数人没有这个权限，也不需要——它只能看到加密字节流，能判断连了哪个 IP，看不到请求内容。

| 观测点 | 能看到 | 看不到 |
|---|---|---|
| 回环（lo / Loopback） | SOCKS5 握手、HTTP CONNECT 明文、请求头 | 客户端之后的加密内容 |
| 物理网卡 | 有没有程序直连真实站点、DNS 查询去哪 | 回环上的本地转发 |
| 上游网关 | 连了哪个 IP、什么时候连的 | 域名、路径、内容 |

顺序建议反过来：先抓物理网卡找「不该出现的直连」，确认没有直连，再抓回环看握手是否成功。先抓回环容易被本地包淹没。

## 四个字段的读法

源地址看「谁发出的」。回环地址或本机内网地址都正常——走系统代理时，业务程序连的就是本机端口，源地址本来就该是本机。真正要看的是目标地址：它应该是后台给的那台代理服务器，不是你访问的网站。

目标端口同样直白。后台给的是 1080、1081、9555 这类，包里就该出现这个数字；出现 443 有两种可能，要么这个代理本来就用 443，要么是浏览器在直连目标站。

第四个字段藏在 TLS 握手里。HTTPS 内容是加密的，但客户端打招呼时会把要访问的域名明文写在 SNI 里。如果连的是代理服务器、SNI 却是目标站域名，说明客户端走的是 HTTP CONNECT 隧道，域名交给代理去解析了。

| 字段 | 走了代理 | 没走代理 |
|---|---|---|
| 源地址 | 本机 / 回环 | 本机（但目标不同） |
| 目标地址 | 代理服务器 IP | 目标站 IP |
| 目标端口 | 后台给的那一个 | 80 / 443 |
| SNI 域名 | 目标站域名（隧道内） | 无独立隧道，直接可见 |

## SOCKS5 握手在包里长什么样

每条连接开头都是一次明文协商：客户端报支持的方法，服务端选定，客户端发账密，服务端回一个结果码。

在回环口抓到的这条流里，方法协商、认证、连接请求都看得见，只有后面的业务数据是加密的。所以「代理有没有在工作」在回环上是可判的，「代理转发得顺不顺」只能靠出口和业务实测。

真正有用的是那个结果码：`0x00` 成功、`0x02` 规则不允许、`0x05` 目标拒绝。抓到码，就抓到结论。

## 三种最常见的误判

第一种是把客户端自己的探测当成业务流量。很多客户端会定期访问自己的服务器报活，那条连接走代理是正常的，但你关心的程序可能完全没走。

第二种是把 DNS 查询当成漏流量。系统代理下 DNS 仍由本机解析，看到 53 端口的查询不代表业务流量漏了；整机接管才会连 DNS 一起转走。

第三种是看到 443 就断定没走代理。有些平台本身就用 443 端口提供 SOCKS5 over TLS，端口一样，握手内容完全不同。

## 不抓包的三条替代路

第一条是出口对照，成本最低：让那个程序自己去访问显示 IP 的页面，把结果和买的代理 IP 比，对不上再往下抓。

第二条是进程级监控，看这个进程的出站连接落在哪个地址端口，不用装抓包工具。

第三条是断网测试：临时把代理客户端退出，如果业务程序立刻报错，说明它确实依赖代理；如果照常跑完，它一直在直连。

## 哪些程序天生不认系统代理

Java 程序读自己的启动参数，不少只在 `-Dhttps.proxyHost` 里认；部分游戏客户端、模拟器、老旧桌面软件只认进程级或全局接管；服务类程序（计划任务、守护进程）根本不读用户会话里的代理设置。

这也是「浏览器好用、业务不通」的根因：两类程序的接管层次不同，靠一个开关同时覆盖它们，本来就不成立。

口径说明：本文判据基于 RFC 1928（SOCKS5）与 RFC 7231（HTTP CONNECT）的协议行为，与站内排查口径一致；平台端口与实现细节以后台显示为准。

## 常见问题

**问：客户端显示已连接，为什么业务程序还是本地 IP？**

答：那个程序没走代理。系统代理只对被接管的那类软件生效，服务类程序、Java 程序、部分游戏客户端要单独配或换整机接管。

**问：浏览器查出来是代理 IP，脚本跑出来却不是？**

答：脚本大概率没读系统代理设置。给它显式传代理参数，或者把接管方式换成虚拟网卡。

**问：抓包看到 443 端口，是不是就没走代理？**

答：不一定。有些平台本身就用 443 提供 SOCKS5，要看握手内容和目标地址才能判断。

**问：抓包抓到 DNS 查询，算漏流量吗？**

答：系统代理下不算，DNS 仍由本机解析。整机接管时才应该连 DNS 一起转走。

**问：不装 Wireshark 能验证吗？**

答：可以。让程序访问显示 IP 的页面做出口对照，最快；其次看进程的出站连接；再不行就退出客户端做断网测试。

**问：为什么有些软件怎么配都不走代理？**

答：它不读系统代理这一层。要么在软件内部填代理，要么用 TUN 整机接管，没有第三条路。
