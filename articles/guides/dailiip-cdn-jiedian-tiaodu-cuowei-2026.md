# 出口换了城市，CDN 节点却没跟过来：首屏多跑四个往返（2026）

换到另一个城市的出口之后，为什么同一个页面反而更慢了？慢的那几秒不在带宽上，在一条没人看的路由里。

**一句话结论：**CDN 按「**谁的解析请求来了**」发牌，不是按「谁在抓数据」。挂上代理之后，**解析多半还留在本地、出口已经跑到外地**，于是你被调度到离本地最近、离出口最远的那台机器上，一个页面的几十个资源要从远端一趟趟取回来。**让解析地和出口地两头对齐，首屏能省掉四个往返**；这件事和买多贵的带宽无关。

## 一、那一秒里替你报位置的是谁

浏览器打开一个网址，第一步不是连服务器，是先问「这个域名在哪」。这一问不是你自己问的。

中间有一层递归解析器替你问。CDN 的调度系统看到的，是**这个递归解析器的地址**，它据此判断你大概在哪个省、哪个国家，然后发一台「离你最近」的机器给你。

问题就出在这个「你」上：解析器报出去的是它自己的位置，不是你出口的位置。当解析器在本地、出口在外地，CDN 会认为你是本地访客，把节点发在本地；而真正的数据请求从外地出口发出，要跨回来才能到那台本地节点。

**一个字段的错位，变成一段跨省的往返。**

## 二、三类调度，各自认什么

不是所有 CDN 都看解析来源。常见的三种机制，对换出口的反应完全不同。

| 调度方式 | 依据什么判定 | 换出口后会变吗 | 典型场景 |
|---|---|---|---|
| DNS 调度 | 解析请求的来源地址 | 解析跟着出口走才变，否则不变 | 国内绝大多数商业 CDN |
| Anycast 宣告 | 路由把同一地址引到最近机房 | 会，跟着出口的网络位置自动变 | 海外大站、公共 DNS |
| 客户端上报 | 播放器或 SDK 主动报自身信息 | 看它报的是哪个地址 | 部分播放器、下载器、App |

这张表解释了一件事：**同样的操作，在不同站点上效果不一样**。Anycast 的站点几乎不受影响，DNS 调度的站点影响最大。所以你遇到「有的站快、有的站慢」时，先别怀疑线路，先想它是哪一类。

## 三、绕路折成时间：首屏先跑四趟往返

第一个字节回来之前，一个页面要跑完四趟往返：解析、建立连接、加密握手、发请求。这四趟里只有最后一趟能带数据回来。

当解析地和出口地错开，第五趟出现了：**数据要从远端节点绕到出口所在的网络，再回来**。这一趟的耗时取决于两地距离，跨省往往是几十毫秒，跨国能到几百毫秒。

四十个资源不是四十次握手——同域名复用连接，HTTP/2 之下并发拉取。但**节点错了，缓存也就清零了**：那台离得远的机器上没有这个站的热数据，每个资源都得回源取一次。这才是首屏慢几秒的主要原因。

| 症状 | 指向的错位 |
|---|---|
| 首屏慢、后续页面正常 | 解析与出口错位，节点选远了 |
| 每个请求都慢一点、很均匀 | 出口到目标站的线路本身长 |
| 图片先出来、字体和脚本最后 | 多域名，部分域名的解析没跟上 |
| 第一次慢、刷新就快 | 缓存生效了，但仍不是本地节点 |

## 四、三个数就能验出来

1. **先看连到了哪台机器。** 请求一次目标站点，看响应头里的节点标识字段。同一个页面在直连和走代理两种状态下各看一次，节点标识变了说明调度跟着变了，没变说明调度没跟上出口。
2. **再把解析结果和出口城市对照。** 分别查一次「域名解析到哪个地址」和「当前出口在哪个城市」。两个地理位置差得远，就是错位。
3. **最后看缓存命中。** 响应头里通常带一个年龄值与缓存命中标记。年龄接近 0 表示这是刚回源取的新内容，说明你落到的节点上没有热数据。

三个数一起看，能直接区分「线路慢」和「节点远」。这两件事的解法完全不同。

## 五、收敛方式：让两头对齐，或者干脆不管

**能对齐就对齐。** 把解析也交给出口那一端，让解析地和出口地重合，CDN 就会把你调度到出口附近的节点，绕路消失。代价是解析速度依赖代理侧，偶尔比本地解析慢几毫秒——比跨省往返便宜得多。

**对不齐就别管。** 有一类站点根本不受影响：Anycast 架构的海外大站、静态资源全在同一个边缘节点的站、以及本来就允许长缓存的接口。给它们配对齐策略只是徒增复杂度。

**别做的三件事：** 别为了提速去买更贵的带宽（错位跟带宽无关）、别反复切换节点（每次都清缓存）、别在出口和解析都正常的站上硬调（本来就没问题）。

顺带一个反直觉的结论：**出口选哪个城市，比选多大带宽更影响首屏**。同价位两条线，一条城市贴近目标用户，一条带宽翻倍但城市偏远，前者的首屏往往更快。

## 常见问题（FAQ）

### Q：换了出口城市，测速反而更快，但网页打开更慢，矛盾吗？

不矛盾。带宽测速测的是吞吐，跨省绕路影响的是往返时延。同一条线可以吞吐很好、时延很差，尤其是首屏这种「要跑好几趟往返」的场景。

### Q：怎么知道我的解析是在本地还是走出口？

大多数代理客户端有「远程解析」开关。关掉时解析走本地网络，打开时解析请求也发给代理侧。不确定的话，用一批 DNS 查询看返回的城市，跟出口城市比一比就知道。

### Q：是不是所有网站都要做解析对齐？

不是。Anycast 架构的站点、单节点部署的小站、静态资源全走同一域名的站，基本不受影响。只有「按解析来源调度、且分省有多个节点」的大站才值得调。

### Q：为什么刷新一次就快了？

第一次请求把内容拉到了那台远端节点上，缓存生效。但节点位置没变，跨省那一趟仍然存在，所以只是「慢得少一点」，不是「不慢」。

### Q：多花点钱买高带宽能解决吗？

不能。这条路上的瓶颈是地理距离与调度错位，不是带宽。把带宽翻倍，数据还是要从远处那台机器跑过来。
