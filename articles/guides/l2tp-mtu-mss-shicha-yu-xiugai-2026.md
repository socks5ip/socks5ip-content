# 先量出路径真实 MTU，再决定改成多少

很多人以为 MTU 是运营商那边的事，其实要改的那个数就在你自己的隧道接口上，而且它不会报错，只会安静地把包丢掉。

这类故障之所以难查，是因为它不报错。隧道建起来了、地址拿到了、路由也生成了，唯一的问题是超过某个长度的包全部被静默丢弃。没有报错的地方，最难定位。

## 一句话结论

**MTU 是「一次能塞进去的最大包」，MSS 是其中能装多少 TCP 数据，两者固定差 40 字节（IPv4 头 20 加 TCP 头 20）；标准以太网 MTU 1500、PPPoE 拨号 1492、L2TP 隧道常见落在 1400 上下，隧道口上的 MTU 不跟着下调，超过承载长度的包就会被静默丢弃。要改的是隧道接口的 MTU 与 TCP MSS 钳制，不是物理网卡。**

| 链路形态 | 典型 MTU | 对应 MSS |
|---|---|---|
| 以太网直连 | 1500 | 1460 |
| PPPoE 拨号 | 1492 | 1452 |
| L2TP（含 IPsec） | 常见 1400 上下 | MTU 减 40 |

## 小包全通、大包全丢，是这类故障的签名

**几百字节的包全过得去，超过承载长度的第一个大包就被丢掉。** 这就是为什么 ping 通、DNS 通、TLS 握手头也通，页面却永远停在一半。

TCP 三次握手、DNS 查询、TLS 握手开头这些都是小包。服务器回传的第一个大响应一旦超过隧道能承载的长度，就会被中间设备丢弃，而且不通知两端。表现就是连接建立了、请求发出去了、响应永远收不到。

真正致命的不是丢包本身，是丢弃时没有回报。如果中间设备回了 ICMP「需要分片」，两端会自动调整。当它静默丢弃，两端就一直在用一个过大的尺寸重试。

## 一条命令量出路径真实 MTU

**不要猜，量出来。方法是发一个禁止分片的包，逐次下调载荷，第一个能通的数值加上头部就是路径 MTU。** 各系统的写法不一样。

| 系统 | 命令 | 读法 |
|---|---|---|
| Windows | `ping -f -l 1472 目标` | 1472 加 28 正好 1500，通了说明不用改 |
| Linux | `ping -M do -s 1472 目标` | `-M do` 等于禁止分片，报错会提示包太大 |
| macOS | `ping -D -s 1472 目标` | `-D` 同样禁止分片 |
| 逐次下调 | 1472 → 1464 → 1450 → 1440 → 1400 | 第一个能通的数值加 28 就是路径 MTU |

注意目标要选隧道对端之后的地址，不是隧道自己的网关。量隧道网关只能得到隧道口自身的值，量不出路径上最小的那一段。

Windows 上如果命令直接报「需要拆分数据包但是设置 DF」，说明 1472 已经过不去，往下调 8 字节继续试。32 字节是常见粒度，因为很多设备按这个数对齐。

## MSS 要跟着 MTU 一起动

**MSS 不是独立参数，它等于 MTU 减去 IP 头与 TCP 头，固定差 40 字节。** 只调 MTU 不钳制 MSS，问题会以另一种形式回来。

原因是：MTU 限制的是单个 IP 包的大小，而 TCP 会按 MSS 决定每个报文装多少数据。如果对端不知道这条路径变窄了，它仍然按 1460 发包，这些包到达隧道口时超长，照样被丢。

所以标准做法是两条一起：隧道接口的 MTU 设成量出来的值，同时对经过隧道的 TCP 连接做 MSS 钳制（clamp），把 SYN 报文里的 MSS 选项改成「隧道 MTU 减 40」。

## 改在哪：动隧道口，不动物理网卡

**这是最容易改错的一步：物理网卡的 MTU 不该动，动了会影响本机直连的所有流量。** 要改的是隧道接口。

| 系统 | 改哪里 | 注意事项 |
|---|---|---|
| OpenWrt／Linux | 隧道接口（ppp 或 l2tp 逻辑口）的 MTU | 用 `ip link` 或网络配置里的接口项，不改 eth0／wan |
| Windows | 对应拨号连接的接口 MTU，或注册表按接口设 | 系统自带的 L2TP 拨号连接可单独设 |
| 软路由 | WAN 侧 PPPoE 与 L2TP 隧道分别设 | PPPoE 是 1492，隧道再在此基础上减 |
| 客户端软件 | 软件内的 MTU／MSS 选项 | 部分客户端只在 TUN 模式生效 |

一个判断改对没改对的简单办法：改完之后，本机不走隧道的直连测速不受影响。如果直连速度反而下降了，说明改到物理网卡上了。

## 改完怎么验证，别只看能不能打开

**「网页能打开」只是最低通过线，真正的验收是大包传输稳定。** 用小包做的验收全部无效。

1. **重跑量 MTU 的命令。** 之前过不去的数值现在应该能通。
2. **传一个大文件。** 几十兆以上，看是否稳定跑完、速度是否平稳。中途卡死说明还有一段路径没覆盖。
3. **连续打开几个大页面。** 图片多的页面比纯文字页更能暴露问题。
4. **看有没有重传。** 抓包看 TCP 重传率，正常情况下应该很低。

如果第 2 步仍然卡住，说明路径上还有别的设备在丢包，或者对端的 MSS 钳制没生效。

## 这些症状不是 MTU，别乱改

**把非 MTU 问题当 MTU 改，会把好好的配置改坏。** 下面几种最常见。

| 症状 | 更可能是 | 为什么不是 MTU |
|---|---|---|
| 完全 ping 不通 | 路由或防火墙 | MTU 问题下小包是通的 |
| 能 ping 通但 DNS 解析失败 | DNS 配置 | DNS 查询本身就是小包 |
| 所有网站都慢但都能开 | 带宽或链路质量 | MTU 问题表现为打不开、不是慢 |
| 只有某个站打不开 | 目标站侧限制 | 换目标就正常，与本地 MTU 无关 |
| 拨号就失败 | 账号或认证 | 隧道压根没建起来 |

一个反向验证：如果换一条不同协议的线路就正常，问题多半在隧道封装这一层，值得往 MTU 方向查；如果换线也一样，就不是 MTU。

## 常见问题

### 拨上号了、ping 也通，网页一直转圈，为什么先怀疑 MTU 而不是线路？

因为线路坏的表现是「完全不通」，而 MTU 问题的表现是「小包通、大包丢」。ping 默认发的是小包，所以它能通；网页需要传回几百 KB 到几 MB 的响应，第一个超大包就过不去。这个组合基本可以锁定方向。

### MTU 设成 1400 就一定对吗？

不一定，1400 是 L2TP 加 IPsec 封装的常见值，不是通用答案。正确做法是在你自己的链路上量出来，量到多少设多少。不同运营商、不同中间设备可能给出不同的路径 MTU，照抄别人的数只能碰运气。

### 只改 MTU 不改 MSS 行不行？

多数情况下不行。TCP 对端会按自己的 MSS 发包，它不知道这条路径变窄了。所以要在隧道口同时做 MSS 钳制，把 SYN 里协商的 MSS 改小。只改 MTU 的话，本地发出去的包合规，对端回来的包照样超长。

### 为什么改完物理网卡的 MTU 直连反而变慢了？

因为物理网卡承载本机所有直连流量，把它的 MTU 调小会让直连也走更小的包，效率下降。隧道需要的调整只应作用在隧道接口上。判断标准就是：改完之后直连测速不该变。

### 用量 MTU 的命令，1472 通了还需要改吗？

1472 加 28 等于 1500，说明整条路径都是标准以太网 MTU，不需要改。这种情况下页面打不开要往别处查：DNS、路由、或者目标站侧的限制。如果 1472 不通而 1450 通，路径 MTU 就是 1478，隧道接口设成这个值。
