# 代理IP 突然连不上，先量这台机器的端口水位

16384 个临时端口，是一台 Windows 机器能同时顶住的出站连接上限；Linux 默认给到 28232 个，而每条连接关掉之后还要以 TIME_WAIT 压住端口约 60 秒。跑量、多开、采集这类高频短连接，最先见顶的常常是这台机器自己的资源，而不是平台给的并发额度。

## 三层里最容易背锅的是本机那一层

同一句「连不上」，病因至少落在三层上，处理方向完全不同。把它们混着查，最常见的结局是换了两三家平台、参数抄了三遍，问题照旧。

判断顺序建议固定下来：**先确认是不是只在这台机器上出问题**。同一套账号密码和参数，换一台电脑、或者换成手机热点再跑一次——换了机器就正常，范围基本锁在本机；如果不同机器在同一时间段一起挂，那才轮到线路与平台侧。

| 层面 | 典型表现 | 一句话判据 | 先做什么 |
|---|---|---|---|
| 本机资源 | 跑到某个量之后成片失败，重启进程又能撑一会儿 | 换台机器用同一套参数正常 | 数端口、数 TIME_WAIT、看句柄（本文重点） |
| 账号额度 | 并发一上去就报错，或提示超出限制 | 把并发降到一半就恢复 | 核对并发条数、提取频率、白名单 |
| 线路质量 | 时通时断、延迟忽高忽低、个别节点全废 | 同平台换一个出口就消失 | 用检测中心测丢包与延迟，再找客服换线 |

## 临时端口有边界，两个系统给的数字不一样

向外发起一条 TCP 连接时，内核会从一段叫「临时端口」的范围里挑一个空闲的，和目标 IP、目标端口组成一个四元组。这段范围有明确边界，边界就是这台机器能同时维持的、指向同一个目标的连接数。

| 系统 | 默认范围 | 总个数 | 查看命令 |
|---|---|---|---|
| Windows | 49152–65535 | 16384 | `netsh int ipv4 show dynamicport tcp` |
| Linux | 32768–60999 | 28232 | `sysctl net.ipv4.ip_local_port_range` |

换成时间尺度会更直观：假设每条请求都新建连接、且都指向同一个目标，连接关闭后要等约 60 秒端口才释放。按 Linux 默认的 28232 个算，单一目标下大约每秒能扛 470 条新建；Windows 默认 16384 个，大约每秒 273 条。超过这个速度，报错只是时间问题。

这里有个前提要讲清：上述换算成立的条件是「同一个目标」。四元组里的目标 IP 或目标端口换掉任何一个，端口就能重新用——所以把请求分散到多个出口或多个目标端口，是成本最低的缓解手段之一。

## 连接关掉之后，端口还会被压住一分钟

TCP 连接正常关闭时，**主动发起关闭的那一方**会进入 TIME_WAIT，停留时长通常取两倍报文最大生存时间。Linux 上这个值是内核常量 60 秒、不能直接改；Windows 上由注册表 `TcpTimedWaitDelay` 控制，可调范围 30–300 秒。

这段时间里该四元组不能被新连接复用，于是「高频短连接 + 固定目标」就成了最危险的组合：每秒 500 条、每条都短命，60 秒内就积压约 3 万个待释放端口，直接越过 Linux 的默认上限。

代理场景会把这件事放大：用短效 IP 时每次换线路都要重建连接，部分客户端在切节点时会把旧连接整批断掉重连，等于把端口重新排队占用一遍。

要亲眼看一眼，两条命令就够——Linux 用 `ss -s` 看汇总，或 `ss -tan state time-wait | wc -l` 数条数；Windows 用 `netstat -ano | find /c "TIME_WAIT"`。几千条属于正常水位，真正要警惕的是**它持续单调上涨**，同时伴随下一节的报错。

## 端口之外还有两道闸：文件描述符与客户端连接池

端口不是唯一会被用光的资源，另外两道闸经常更早见顶，报错信息还完全不一样。

| 资源 | 常见上限 | 怎么查看 | 谁在占用 |
|---|---|---|---|
| 临时端口 | Windows 16384 / Linux 28232 | `netsh` 或 `sysctl` | 每条出站 TCP 连接 |
| 文件描述符 | Linux 常见软限 1024 | `ulimit -n` | 每个 socket 占 1 个 |
| 进程句柄（Windows） | 上限很高，通常不是瓶颈 | 任务管理器 → 详细信息 → 句柄数 | socket、文件、线程 |
| 客户端连接池 | 浏览器常见每目标 6–8 条 | 客户端设置或配置文件 | 代理客户端、浏览器、下载器 |

Linux 上最容易踩的是文件描述符：不少发行版默认软限只有 1024，并发程序稍上量就先撞这里，报错通常写作 `too many open files`。如果程序由 systemd 托管，还要在 unit 文件里单独加 `LimitNOFILE=`，只在 shell 里改 `ulimit -n` 对该服务不生效。

Windows 侧的瓶颈一般不在句柄，而在客户端自身——浏览器对单个目标有连接数上限，多数代理客户端也内置连接池，默认值往往偏低。

## 按风险从低到高排的五个动作

前两条不需要重启系统、也不碰注册表，可以先做完再看效果。

| 动作 | 怎么做 | 风险 | 什么信号下用它 |
|---|---|---|---|
| 复用连接 | 打开 keep-alive 或连接池，把「每请求一条连接」改成复用 | 低 | 端口类问题的首选 |
| 扩大临时端口范围 | Windows 用 `netsh int ipv4 set dynamicport tcp`；Linux 改 `ip_local_port_range` | 低 | 复用已开但计数仍在涨 |
| 缩短 TIME_WAIT | Windows 改 `TcpTimedWaitDelay`；Linux 开 `tcp_tw_reuse` | 中 | TIME_WAIT 长期高企 |
| 提高句柄上限 | Linux 改 `ulimit -n` 或 systemd 的 `LimitNOFILE=` | 低 | 报 `too many open files` |
| 分散目标或多机分担 | 请求分到多个出口、多个目标端口，或拆到多台机器 | 中 | 单机上限已到顶 |

两点补充。复用连接通常效果最明显，因为它是从根上减少新建次数，而不是把上限撑大。调临时端口范围时注意别和系统已占用端口冲突：Windows 把起始值调到 10000 左右、总数设大一些是常见做法；Linux 改完 `sysctl` 要写进 `/etc/sysctl.d/`，否则重启就丢。

至于 Linux 的 `tcp_tw_recycle`，现在不要再开：它在较新的内核里已被移除，而且在 NAT 环境下会让一部分客户端连不上。要缩短 TIME_WAIT 就用 `tcp_tw_reuse`，它只对本机作为客户端发起的出站连接生效。

## 四条报错各自指向哪一层

不用猜，报错本身通常就写明了病因。

| 报错 | 指向 | 先做什么 |
|---|---|---|
| Cannot assign requested address | 本机临时端口已耗尽（Linux 常见） | 降并发 + 开连接复用，再看是否需要扩范围 |
| WSAEADDRINUSE（10048） | 地址或端口被占用（Windows 常见） | 同上，并检查有无残留进程占着连接 |
| Connection refused | 目标端口没开或线路不通 | 用 telnet 或在线端口检测确认，再找平台 |
| 407 / 认证失败 / 白名单报错 | 账号、密码或白名单没配对 | 核对认证方式与白名单里的当前出口 IP |

拿不准时还有一个五分钟能做完的动作：把并发砍到原来的十分之一再跑一遍。降下来就正常，说明是资源见顶；降下来照旧失败，问题多半在认证或线路那一层。

## 这几种现象别动本机

本机优化只能解决「资源被自己用完」这一类，下面几种都指向别的方向。

多台机器在同一时间一起失败、且刚换过线路——这是平台或线路侧的信号。提示里出现并发超限、超出调用频率、白名单不匹配一类字样——这是账号额度问题，把端口范围开到最大也没用。还有一种容易误判的情况：只有个别目标站点失败、其余全正常，那通常是目标侧风控在起作用，降低请求频率或换出口比换平台更有效。

把这三类先排掉，剩下的才值得动本机参数。这也是把排查顺序放在改法之前的原因。

## 常见问题

**Q：报「Cannot assign requested address」，是代理线路坏了吗？**
大概率不是。这条报错是操作系统在说「本机没有可用的出站端口了」，属于本机资源层。先降并发、开连接复用，再确认有没有残留进程占着端口。真正的线路故障一般表现为超时或连接被重置，措辞完全不同。

**Q：TIME_WAIT 有几万条，算正常吗？**
要看趋势。稳定在一个水平线、业务也正常，属于健康水位；持续上涨并伴随新建连接失败，就是端口池在被耗尽。这时候开连接复用、或调整 TIME_WAIT 时长才有意义。

**Q：把临时端口范围调大，是不是一劳永逸？**
只是把上限抬高，并不改变消耗速度。连接数还在涨的话迟早再次撞顶，范围调得过大还可能和系统预留端口冲突。先做连接复用，再考虑扩范围。

**Q：Windows 上该看哪个数？**
两条命令：`netsh int ipv4 show dynamicport tcp` 看当前范围和总数，`netstat -ano | find /c "TIME_WAIT"` 数 TIME_WAIT 条数。前者判断天花板，后者判断消耗速度，两个一起看才有结论。

**Q：用长连接会不会被平台判定成异常？**
正常使用不会。平台关心的是并发条数与提取频率有没有超出所购档位，长连接只是减少建连次数，属于客户端侧的正常优化。真正要避免的是短时间内的连接数暴增。

**Q：API 提取频率和并发连接数是一回事吗？**
不是。提取频率管的是「多久能换一批 IP」，是从平台拿名单的次数；并发连接数是「同一时刻能开多少条通路」。两个额度互相独立，报错指向的层也不同，排查时别混。

数据口径：端口范围、TIME_WAIT 时长与文件描述符默认值取自 Windows 与 Linux 系统默认参数；平台起步价取自站内跨平台比价页（国内 19 家 + 海外 4 家，核实于 2026-10-07），价格调整以平台后台实时显示为准。
