# 六个口子里只有一个在读

六个接口，是取 IP 的，还是管线路的？答案偏后者——只有一个负责读，另外五个都在改。奔富IP（官网 benfuip）的开放接口文档版本 v1.0.2，服务器地址 `api.benfuip.com`，把一条线路的整个生命周期都放了出来：取线、换线、写备注、改密码、解绑，外加一个查代理商 ID 的口子。这意味着脚本能做的事不再只是批量拿 IP 再手动填进工具，而是把线路当成可编程资源——自己发现异常、自己换、自己记账。**真正稀缺的不是「有 API」，而是把取线之外的那几个动作也开放出来。**

## 一句话结论

奔富IP 的 API 共 **6 个接口**，统一用 `userid + apikey` 认证，全部支持 GET 与 POST。取线接口能按协议、线路 ID、备注三个维度过滤；换线接口用 `cityid` 控制换到哪；剩下四个接口把线路当成资产来管。**两个必须记住的坑**：接口失败时 HTTP 状态码依然是 200，真正的原因写在返回体的 `errcode` 与 `msg` 里；密钥需要注册后联系客服开通，它等于账号权限，不能放进前端。

| 接口 | 做什么 | 关键参数 |
|---|---|---|
| `ipuserList` | 读取账号下的线路列表 | `pt` / `ipid` / `remark`（都可选） |
| `ipuserChangeCity` | 把某条线路换到别的地区 | `ipid` + `cityid` |
| `ipuserSetRemark` | 给线路写备注 | `ipid` + `remark` |
| `ipuserSetPassword` | 改线路的连接密码 | `ipid` + `newpass` |
| `ipuserUnbind` | 解绑线路 | `ipid` |
| `getAgentid` | 查账号的代理商 ID | 无额外参数 |

## 一、六个口子里，五个都在改线路的状态

取线接口的返回值里，`host`、`port`、`ipid`、`pwd` 是拿来连的，另外几个字段是拿来判断的。省事的地方在于三个可选过滤参数——不必全量拉回来再自己筛，直接在请求里指定就能只拿到需要的那一批。

| 返回字段 | 实际用途 |
|---|---|
| `outip` | 和上次记录比对，判断线路是否被系统换过出口 |
| `enddate` | 提前几天列出即将过期的线路，避免跑到一半断线 |
| `cityid` / `cityname` | 核对线路当前落在哪个地区，与业务要求是否一致 |
| `remark` | 配合过滤参数，把线路按业务分组取回 |
| `pt` | 按协议筛：socks5 / http / pptp / l2tp / sstp 五种可选 |

把它接成一个每天跑一次的巡检脚本，只需要四件事：拉全量列表、比对 `outip` 有没有变、算 `enddate` 还剩几天、把异常线路记进日志。这一步不需要任何复杂判断，纯字段对比就能把「线路悄悄换过出口」和「快到期忘了续」这两类事故提前拦下来。

## 二、过滤参数填对了，就不必拉全量回来自己筛

`cityid` 用一套约定值覆盖了五种完全不同的换线意图。不把这几个值弄清楚，很容易写出「每十分钟换一次、每次都换到随机地区」的脚本——那既浪费额度，也会让业务侧的出口频繁漂移。

| cityid | 含义 | 什么时候用 |
|---|---|---|
| `0` | 随机 | 只要求换个出口，不在意落在哪个地区 |
| `-1` | 随机 P 节点 | 要住宅拨号型出口，接受地址不固定 |
| `-2` | 随机 T 节点 | 要稳定型出口，不挑具体城市 |
| `-3` | 随机 G 节点 | 偏游戏 / 低延迟场景；文档注明部分套餐不可用 |
| `-999` | 相同城市切换 | 业务要求城市不变、只换地址，最省心的一个值 |
| 大于 0 | 指定城市 | 有明确目标地区，比如固定在某市 |

这套取值让「触发式换线」变得可行：不要按时间盲换，而是在业务侧收到明确信号（连续请求被拒、页面出现验证、延迟突破阈值）时才调用一次换线接口，并按业务性质选 `-999` 或 `-1`。换线次数花在真正需要的时候，出口也不会无意义地满地图乱跳。线路本身的切换额度怎么算，站内的奔富IP 切换与分组管理教程比接口文档讲得更细，动手写脚本前值得先看一眼。

## 三、cityid 那几个负数，各自代表哪种换线意图

备注接口最容易被当成可有可无的一个，但它其实是把接口用顺手的分水岭——因为取线接口支持按 `remark` 过滤。先写备注、再按备注取，这个顺序很关键；反过来做，就只能每次把整个账号的线路全拉回来，靠代码猜哪条属于哪个业务，线路数量一上去维护成本就成倍增加。

| 业务场景 | 备注怎么写 | 取线时怎么调 |
|---|---|---|
| 多店铺 / 多窗口 | 店铺编号或窗口号，做到一店一线可追溯 | 按 `remark` 取回该店的线路，再写进对应窗口的配置 |
| 采集 / 抓取 | 按任务批次打标，例如任务名或批次日期 | 按 `remark` 拉本批次的线路池，失败任务单独换线 |
| 软路由 / 服务器 | 按设备或网段打标，标明这条线给谁用 | 定时拉取后直接重写分流规则，不用人工对照 |
| 测试与正式分离 | 测试线单独打一个前缀，避免混进生产池 | 按协议或备注分别取，测试线不参与正式任务 |

改密码与解绑这两个接口处理的是凭据本身的变化，属于低频但必须做的动作，最典型的三个触发点：设备或工具交接时把原凭据作废、怀疑凭据外泄时立即轮换、线路不再使用需要从账号里摘掉。用接口做的好处是有据可查——手工改一次密码，事后很难说清改过哪些线路；走接口能留下执行记录，配合备注里的业务标记，可以直接回答「哪条线在什么时候被换过凭据」。

## 四、先打备注再取线，顺序反了就得靠代码去猜

| 检查项 | 实测结果 | 说明 |
|---|---|---|
| 不带参数请求取线接口 | HTTP 200，内容为 `errcode 1` | 状态码正常，错误在 body 里 |
| 不带参数请求代理商接口 | HTTP 200，内容为 `errcode 1` | 同样的返回形态，需统一处理 |
| 带参数的正常请求 | `errcode 0`，`data` 内为业务数据 | 判断成功看 `errcode`，不要看 HTTP 码 |

落到代码里就一句话：请求发出去之后，先看 `errcode`，为 `"0"` 才去读 `data`，否则把 `msg` 原样记进日志。反过来写（只看 HTTP 200 就当成功）会让脚本在参数写错的情况下继续往下跑，最后表现为程序没报错、但线路一直连不上，排查起来最费时间。

## 五、状态码 200 也可能是失败：判 errcode

每个奔富账号都可以有自己的独立密钥，但它不是自助生成的：需要通过官方入口注册（邀请码 **adminA1**）之后联系客服开通。开通后它就是账号级凭据——拿到 `userid` 与 `apikey` 等于拿到这个账号下线路的读改权限。

| 保管动作 | 建议做法 |
|---|---|
| 存放位置 | 服务端环境变量或权限受限的配置文件 |
| 调用来源 | 只从自己的服务器发起，避免走公共网络环境 |
| 交接与轮换 | 人员或设备变动时重新签发，并同步轮换线路密码 |
| 异常处置 | 发现疑似外泄，先改账号密码并联系客服，必要时逐条解绑 |

三条底线：密钥写死在服务端的定时脚本里，不要嵌进网页前端或手机客户端；不要提交到公开的代码仓库；不要把带密钥的完整请求链接贴进群聊或工单。

## 常见问题

**Q：六个接口里日常最常用的是哪一个？**
取线接口。它是唯一一个「读」的接口，其余五个都要先拿到 `ipid` 才会用到，所以实际写脚本时通常先调它，再从结果里挑出要处理的那条线路。

**Q：接口能把别的账号的线路也取出来吗？**
不能。认证参数是 `userid` 加 `apikey`，接口只作用于这组凭据对应的账号，返回的也是该账号名下的线路。

**Q：换线时指定 -3 随机 G 节点，为什么有时会失败？**
文档明确写了部分套餐不能使用 G 节点。拿到失败返回时，先确认账号买的档位是否包含 G 节点，再去看网络或参数问题。

**Q：接口返回失败，但 HTTP 状态码是 200，怎么判断？**
判返回体里的 `errcode`：为 `"0"` 才算成功并去读 `data`，为 `"1"` 就把 `msg` 记进日志。只看 HTTP 200 会让参数错误被静默放过。

**Q：没有 API 密钥，还能正常用奔富IP 吗？**
能。密钥是给批量与自动化场景准备的；电脑端、安卓 APP 与软路由都可以在后台或客户端手动提取线路，日常单机使用不需要接口。

**Q：取线接口返回的 enddate 和 outip 具体能拿来做什么？**
做巡检。每天拉一次列表，比对 `outip` 是否与上次记录一致、算 `enddate` 还剩多少天，就能在线路被换过出口、快到期这两件事变成故障之前收到提示。
