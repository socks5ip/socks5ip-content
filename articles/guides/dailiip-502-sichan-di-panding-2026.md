# 代理IP 报 502：先看有没有状态行，再决定换不换线

打开报错那一屏先别关：状态行有没有数字、错误页是谁写的、响应头里的 Server 指向哪一跳，这三处能把产地缩到一处，比再买一条线快得多。

**502 只会出现在链路已经通到某个 HTTP 服务的时候，它证明的是这条路通，不是断。本机实测三种「没有状态码」的失败分别是 curl exit 7、52、28；能拿到 HTTP/1.1 502 时，问题已经跑到这条链路之后了。**

| 屏幕上的样子 | 产地大概率在 | 有没有状态行 |
|---|---|---|
| 只有 curl 错误码（7 / 52 / 28） | 还没走到 HTTP 服务，链路或端口问题 | 没有 |
| 502 + 代理软件自己的英文错误页 | 你这侧的 HTTP 代理 | 有 |
| 502/504 + CDN 的缓存标记 | CDN 边缘回源失败或等超时 | 有 |
| 503 + Retry-After | 平台或源站暂时不接活，换线无用 | 有 |

数据来源：全网低价IP 本站实测，本机自起端口复现三种无状态码失败（2026-11-24 核对）｜错误页样式以实际响应为准

## 先看屏幕上有没有状态行，这一步决定排查方向

**有状态行说明「有人回了话」，排查对象是链路之后的某一跳；没有状态行说明连话都没说上，排查对象是出口、端口和代理进程。**

本机把三种无状态码的失败逐个复现了一遍，都在本地回环端口上，与线路质量无关：端口没人监听是 exit 7，连上立刻 close 是 exit 52（Empty reply），收下连接但永不回应是 exit 28（超时 0 字节）。三种都在状态行之前就结束了。

这一区分之所以关键，是因为两类故障的排查顺序几乎是相反的：没有状态码时去查出口和端口有意义；拿到 502 时再去换线，等于在一个已经通了的路段上找断点。

还有一层：接入方式决定「谁有资格给你状态码」。SOCKS5 按 RFC 1928 只在协商阶段回一个单字节 REP 码，之后退化成纯字节管道，此后目标站回什么，客户端就原样看到什么——所以 SOCKS5 下看到 502，一定是更远端给的。换成 HTTP 代理（含 CONNECT）就不一样，代理本身就是网关，有能力、也确实会自己造一个 502。

## 四个产地各自的笔迹：错误页、响应头、换直连还复不复现

**本侧 HTTP 代理吐的是几十到几百字节的英文短页，Server 写它自己的名字；CDN 边缘的错误页带品牌样式和缓存状态字段；源站前置（nginx）只有一行默认页；应用层自造的错误页带着站点模板，看着像正常页面。**

四个产地里只有第一个和你手上的代理有关。这也是「一报 502 就换线」经常白花钱的原因：四条里三条换线都没用，偏偏大家最常动的就是线。

判断时可以借一个动作：临时改直连再请求一次。本侧代理造出来的 502 会消失，其余三类照样复现——因为它们发生在代理之后。这个动作不需要任何工具，改一次系统代理设置就行。

| 产地 | 错误页长相 | 直连还复现吗 | 该动哪里 |
|---|---|---|---|
| 你这侧 HTTP 代理 | 英文短页，无站点样式 | 不复现 | 查代理上游、看代理日志 |
| CDN 边缘 | 品牌页 + 缓存标记 | 基本复现 | 换节点或等，别换线 |
| 源站前置 nginx | 一行默认页 | 复现 | 与你的网络无关，等站方 |
| 应用层自造 | 带站点模板的完整页 | 复现 | 看站方公告 |

## 502 与 503 该动的方向相反，504 是有人等太久

**502 是上游回了但回得不对，503 是服务还在、暂时不接活，504 是某一跳等下游超时。三者的第一动作分别是查中间那段对话、读 Retry-After、以及分辨是谁在等。**

502 的典型触发是上游连接被提前关闭：前置把请求转给应用进程，进程在处理中被杀或达到上限不再接，前置立刻回 502。这类错误多一半是目标站自己的事，换十条线也是同一个结果。

503 的含义完全不同，常见于过载、维护、额度用尽或并发打满，有些平台会附一个 Retry-After 告诉你多久后再来。看到 503 的第一动作是读这个头，不是换线。

504 则要问「谁在等谁」：代理等目标站、CDN 等源站、还是你的客户端等代理。定位方法一样——换直连看是否复现，复现就往远端推一层。

## 三个对照实验，两分钟缩到一个产地

**换直连、换出口、换客户端，三个变量一次只动一个；哪一步现象变了，产地就在那一步涉及的那一层。**

换直连：502 消失，产地在本侧代理；仍然复现，往后推。换出口：换一条完全不同地区的线，如果是「出口被目标侧针对」，表现会变；源站自身 5xx 则完全不变。换客户端：把 curl 换成浏览器、或把 HTTP 代理换成 SOCKS5，能区分「代理模式造成的」还是「目标站本身如此」。

三个实验的顺序建议是直连 → 换出口 → 换客户端。顺序反了会混入新变量：先换线路，你分不清是线路变了还是时间变了。

## 只有一类 5xx 值得花钱换线

**出口 IP 被目标侧限流或拉黑这一类值得换；源站自己 5xx、CDN 回源失败、应用层报错这三类，换多少条线都是同一个结果。**

判断是不是第一类，看一个特征：换出口后错误率明显下降，且旧出口在别的站点上一切正常。这基本就是「这个 IP 在那家眼里有问题」，换线是正解。

反过来，如果换个出口照样 502、甚至直连也 502，那就别再买线了。这时候该做的是把响应头和错误页截图整理好，交给平台或站方——大部分情况下，问题不在你这一侧。

## 常见问题

**问：代理返回 502 是不是线路挂了？**
答：不是。502 说明链路通到了某个会回话的服务，线路本身是通的；挂了的表现是没有状态行。

**问：SOCKS5 下也会出现 502 吗？**
答：会，但一定来自更远端。SOCKS5 协商完成后只做字节转发，不会自己造 502。

**问：换一条线还是 502，说明什么？**
答：说明产地不在你这侧。源站、CDN 或应用层的问题，换多少条线都一样。

**问：503 和 502 要不要都换线？**
答：都不建议先换。503 先读 Retry-After 并降并发，502 先看错误页是谁写的。

**问：怎么快速判断是不是被目标站针对？**
答：同一时间用另一条出口请求同一地址，若恢复正常，就是出口 IP 的问题。

**问：并发一高就出 5xx，是代理不稳吗？**
答：多一半是目标侧限流或源站扛不住；先降到单线程复测，再看是否复现。
