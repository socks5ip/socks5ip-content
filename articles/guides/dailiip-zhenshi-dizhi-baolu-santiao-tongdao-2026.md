# 代理换了，本机地址为什么还会被看到

换个更贵的档位就能堵住，还是出口那条线本来就不算漏口？当同一个检测页先给出你买的那条出口、再翻出家里宽带的地址时，缺的从来不是预算——**域名解析、UDP 旁路、IPv6 这三条通道只要有一条在直连，换哪一档都补不上**。

## 谁在看，能看到什么：先把两侧分开

「地址暴露」这四个字里其实混着两个方向：一种是对方真的拿到了你的本机地址，另一种是「我觉得它认出我了」。前者属于网络层，后者多数跟 IP 无关。先分清两侧，后面的动作才不会白做。

| 谁在看 | 正常情况下能拿到 | 什么时候会拿到本机地址 |
|---|---|---|
| 目标网站 / 应用服务器 | 出口 IP、出口所属运营商与地区 | 只有三条通道之一在跑时才会 |
| 你访问的 DNS 服务器 | 你本地的 DNS 归属（取决于解析在哪做） | 解析请求走本地出口时必然拿到 |
| 同一网络里的其他程序 | 内网地址、部分场景下的公网地址 | UDP 直连（WebRTC 的 STUN 探测就是这一类） |
| 代理平台侧 | 账号、连接时间、用了哪条线路 | 一直都有，这与「匿不匿名」是两件事 |

一句话记法：**平台看的是出口，本机地址只在「绕过去的那部分流量」里出现**。这也解释了为什么反复换 IP 却没有改善——问题根本不在出口那条线上。

## 漏口一：解析这一步留在了本地

输入一个域名，程序得先把它翻成 IP 地址。代理工作在连接层，解析请求走不走代理，取决于客户端有没有开「远程解析」——不是所有代理类型都会顺手把它接管。

| 客户端配置 | 解析在哪里做 | 结果 |
|---|---|---|
| HTTP / HTTPS 代理 | 一般本机解析完再发 CONNECT | 网页出口换了，解析记录仍来自本地运营商 |
| SOCKS5，未开远程解析 | 本机解析 | 出口干净，解析没换 |
| SOCKS5，开了远程解析 | 由代理侧完成 | 解析与出口同源，两边对得上 |

命令行侧的写法很直白：curl 一族用带 h 的 `socks5h://`，末尾那个 h 就是「交给远端解析」；浏览器侧则是各自客户端的远程解析开关。这条要紧的原因在于，解析归属与出口归属对不上本身就是一条显著特征——出口落在洛杉矶、解析节点却在国内，这种拓扑比「用了代理」更扎眼。

## 漏口二：UDP 那一路多数应用层代理接不住

网页浏览走 TCP，应用层代理接得住；但实时音视频、语音、游戏，以及浏览器里那套做点对点连接的机制天生走 UDP。代理只管住了 TCP，UDP 就只能从本地网卡直连出去。浏览器这一路最典型的表现就是 STUN 探测：它向公网服务器发一个包，只为问一句「我在外面看起来是什么地址」。

| 场景 | 走什么 | 代理接不接 | 本机地址会不会露 |
|---|---|---|---|
| 普通网页、接口请求 | TCP | 接得住 | 不会 |
| 浏览器音视频 / 点对点连接 | UDP（STUN 探测） | 多数 HTTP 代理不接 | 会 |
| 游戏、语音通话 | UDP 为主 | 看协议与平台是否放开 UDP | 看是否走代理 |
| 大批量下载 / 上传 | 多为 TCP | 接得住 | 不会 |

站内比价页把协议分成两组写：SK5 + HTTP 属应用层代理，注明支持 UDP；L2TP + PPTP 是隧道协议，系统级、整机走代理。所以这一路的处置落在两个动作上：要么把它交给真能转发 UDP 的协议，要么在客户端里直接关掉。Firefox 可以整体关闭实时通信能力；Chrome 一侧没有面向普通用户的开关，得靠策略或扩展限制不走代理的 UDP。关得越彻底，浏览器行为与真实用户差异越大，所以只在确实需要时才动。

## 漏口三：只接管 IPv4 的线路拦不住双栈宽带

这是三条里最少被提起的一条。不少宽带是双栈的，本机同时有 IPv4 与 IPv6 两个地址；目标站点也开了 IPv6 时，客户端很可能优先走 IPv6。而大量线路只接管 IPv4——于是你以为所有流量都过代理了，实际上走 IPv6 的那一半是直连。

| 本机网络 | 线路是否接管 IPv6 | 实际结果 |
|---|---|---|
| 只有 IPv4 | 不存在这条漏口 | 无风险 |
| 双栈 | 只代理 IPv4 | 走 v6 的连接直连，IPv6 地址暴露 |
| 双栈 | IPv6 也被接管 | 两侧一致，无漏口 |

判据很便宜：直连时查一次本机有没有 IPv6 地址，挂上代理后再看出口是不是同一个版本。要堵有两条路，链路侧选能同时接管 v4/v6 的线路、或在客户端里关掉 IPv6；本机侧直接禁用网卡的 IPv6。

## 三条漏口的判据与堵法，一张执行表收口

把前面三节压成一张可执行的表：左边是一次能做完的判据，右边是对应的堵法。顺序不建议调，因为第一条最容易被误判成「代理没生效」。

| 通道 | 一次判据 | 堵法 | 不堵的后果 |
|---|---|---|---|
| 域名解析 | 解析节点归属是否与出口同地区 | 改用远端解析（带 h 的写法 / 客户端开关） | 解析记录留在本地，拓扑对不上 |
| UDP 旁路 | 实时音视频 / P2P 场景下出口是否变回本机 | 换成真转发 UDP 的协议，或在客户端关掉这一路 | 本机公网地址被对端拿到 |
| IPv6 | 本机有 v6 时看出口是否同一版本 | 线路侧接管 v6，或本机禁用 v6 | 走 v6 的那部分直连 |

还有一条不属于「通道」但常被一起问：程序压根没读代理设置。系统里那份手动配置只有一份，跟随它的程序共用同一个出口，而自带网络栈的游戏客户端、下载器、部分桌面软件多数不读它——它们会直连。要覆盖全机，得换到系统级或路由级的接法。

## 自测顺序：直连与挂代理各留一份读数

不用装软件，站内检测工具就是按这个顺序设计的：先测通不通，再看 IP 属于哪一类，再判断能不能干某件事，最后排查是不是自己宽带的问题。关键是每一步都把直连的读数也留一份。

| 顺序 | 做什么 | 看什么 | 合格的样子 |
|---|---|---|---|
| 1 | 线路可用性检测 | 真实握手通不通、出口归属、延迟分级 | 能连上，出口落在你买到的地区 |
| 2 | IP 质量检测 | 住宅还是机房、纯净度 | 与业务要求相符，不是黑名单段 |
| 3 | 业务场景模拟 | 六类场景的适配评分与硬门槛 | 目标场景那一项过线 |
| 4 | 宽带测速 | 下载 / 上传、延迟、抖动、丢包 | 与直连那次对比，差值在可接受范围 |

测速页的网络评级口径是延迟 25 + 抖动 15 + 丢包 15 + 下载 20 + 上传 15，满分 100；参考区间是延迟低于 30ms 算优秀、抖动低于 5ms 算稳、丢包 0% 最理想。这里有个容易忽略的细节：**上传测的是「设备往外发」的能力，直播、传文件、云备份真正吃的是这一项**，只看下载数字会误判。这四款工具都不用注册，也不限次数。

## 这几类限制跟本机地址无关，别堵错方向

工具查完发现三条通道都干净，平台却还是给了限制——这时候别再折腾线路。风控看的从来不止 IP 一项。

| 现象 | 真实原因多在 | 该动的方向 |
|---|---|---|
| 检测页写着「是代理」 | 线路类型本身是公开的机房段 | 换类型，不是换数量 |
| 同一批号互相牵连 | 几条出口其实落在同一个 C 段 | 分段，而不是继续加条数 |
| 换了 IP 仍被认出来 | 浏览器指纹、设备特征没换 | 环境一致性 |
| 提示环境异常 / 限制登录 | 账号历史、行为节奏、登录地突变 | 按四项网络环境逐条排查 |

这里也说清一句边界：代理带来的「看不到」是相对目标站点而言的；平台侧的账号、连接记录一直都在，服务本身由第三方平台提供，须依法使用。想彻底「不存在」，技术上没有这回事。

## 预算三段：堵到哪一层够用

三条通道要不要都堵，取决于你怕的是哪一种暴露。多数国内业务只碰 TCP，真正需要动到 UDP 与 IPv6 的，是带实时通信或跑海外站点的场景。

| 起步价区间 | 代表平台（最低档） | 协议情况 | 适合堵到哪一层 |
|---|---|---|---|
| 3 元以内 | 光梭IP 2.24 ／ 奔富IP 2.6 ／ 烽讯IP 2.6 ／ 蛟龙IP 2.8 | 多协议齐全 | 解析 + 常规 TCP，先试水 |
| 4 ~ 6 元 | 沧海IP ／ 光子IP ／ 天机IP 4；天行IP ／ 鲸云IP ／ 优享云IP 6 | 隧道与应用层代理各有 | 解析 + UDP + 整机场景 |
| 7 元以上 | 优众IP 7.2 ／ ST加速器 12 ／ 酷熊IP 20 | 多协议 + 更细的切换额度 | 多层一起堵，含游戏专线 |
| 海外线路 | 全球代理IP 5 ／ 无双IP 7.5 ／ 皇冠IP 12 ／ 55游 15 | 以住宅静态为主 | 解析 + IPv6 + 属地一致 |

挑的时候先看协议这一列：需要整机或路由器走隧道的，认准带 L2TP / PPTP 的那一档；只装在浏览器或单个软件里用的，看 SK5 + HTTP 就够。比价页上那组数字核实于 2026-09-13，平台会不定期调价或做活动，下单前以平台后台实时显示为准。多数平台都留了测试额度，别跳过验证这一步。

## 常见问题

**Q：挂了代理，检测页显示的还是本地 IP，是不是买到假线路了？**
先别怀疑线路。按顺序查三件事：客户端有没有真的启用代理、解析是不是留在了本地、UDP 或 IPv6 是不是绕过去了。站内检测工具走的是真实握手而不是 ping，能看到出口到底是谁；如果出口正确、只是某个页面显示本机地址，那基本是后两条通道的问题。

**Q：为什么 SOCKS5 也挡不住浏览器里的实时通信？**
因为那一路是 UDP。站内比价页把 SK5 + HTTP 归到应用层代理并注明支持 UDP，但客户端这一侧还得看有没有把这部分流量交给它；多数场景下更省事的做法是在浏览器里关掉实时通信能力，或在策略层限制不走代理的 UDP。

**Q：只挂浏览器代理，其他软件会不会露？**
会。系统里那份手动代理只有一份，跟随它的程序共用同一个出口，而自带网络栈的游戏客户端、下载器、部分桌面软件多数不读它——它们会直连。要覆盖全机，得换到系统级或路由级的接法。

**Q：检测中心显示「是代理」，是不是说明这条线不干净？**
两件事。显示「是代理」说的是这段地址的公开属性，多数机房段就是公开可查的，不代表这条线不可用；真正影响业务的是纯净度与有没有进过黑名单。工具结果本身也只是实时抽样评估，实际风控还受浏览器指纹、账号历史影响，只能当参考。

**Q：IPv6 要不要直接关掉？**
看业务。只做国内、目标站点也没有 IPv6 的，关不关影响不大；跑海外站点、本机又是双栈宽带的，建议要么让线路把 IPv6 一起接管，要么在本机禁用 IPv6，别让它一半走代理一半直连。关之前先用检测工具留一份读数，改完再测一次对比。

**Q：三条通道都堵上了，平台还能找到我本人吗？**
网络层能做到的是「目标站点只看到出口」。但代理平台侧的账号与连接记录一直都在，实名认证也是行业常规，服务本身由第三方平台提供，须依法使用。正确的预期是「对外一致、可核验」，而不是「技术上不可追溯」。
