# 采集跑到一半全超时：先算本机端口再换线路

为什么把带宽从 5 兆加到 100 兆，报错还是那句「分配不到地址」？这类原话指向的位置不在对面，在这台机器的临时端口池里。

同一台采集机跑到第 3 万条开始清一色报错，换过三条线路、把带宽从 5 兆加到 100 兆，报错一个字没变。这类现象只有一个解释：瓶颈不在对面，在本机。

**Linux 默认只给 28,232 个临时端口，TIME_WAIT 压 60 秒，理论每秒 470 条新连接、实测打七折约 330 条；Windows 默认 16,384 个、压 120 秒，只有每秒 137 条。并发撞到这条线，加带宽一分钱作用没有。**

| 系统与状态 | 端口范围 | 可用端口 | TIME_WAIT | 理论每秒 | 实测七折 |
|---|---|---|---|---|---|
| Linux 默认 | 32768–60999 | 28,232 | 60 秒 | 470 条 | 约 330 条 |
| Linux 调优后 | 10240–65000 | 54,761 | 60 秒 | 912 条 | 约 640 条 |
| Windows 默认 | 49152–65535 | 16,384 | 120 秒 | 137 条 | 约 95 条 |
| Windows 调优后 | 10000–65535 | 55,536 | 120 秒 | 463 条 | 约 325 条 |

数据来源：全网低价IP 实测（dataset_id: S5-PORT-4TUPLE）｜系统默认值取自内核文档与 Windows 官方说明，核对日期 2026-11-21

## 走代理之后，四元组只剩一个变量

**一条连接的身份由源 IP、源端口、目标 IP、目标端口四样拼成，全站流量塞进同一个代理入口后，前三样都被钉死，只剩源端口还能变。**

直连时同一台机器可以用同一个源端口去连一百个不同的目标站，因为目标那一维每次都不同，四元组不冲突，端口池等于被放大了一百倍。一旦所有流量都从同一个代理入口出去，目标那一维也被固定成「代理服务器 IP + 代理端口」。

于是 28,232 这个数字从参考值变成硬顶：它不再被一百个目标分摊，而是全部流量挤在一根管子里排队用的号牌。号牌发完，新的 connect 调用连第一步都迈不出去——注意，这时候你的线路完全是好的，服务端一条连接都没收到。

这也解释了一个常年被误解的现象：同一套脚本不走代理时 500 并发毫无压力，一挂上 SOCKS5 就开始零星报错。不是代理不行，是客户端这一侧的地址空间被压扁了。价目表上有些平台标「多端口」「多入口」，本质就是给你不止一个代理地址，等于把一维重新变回多维。

## 三个数字决定上限

**每秒能新建多少连接 ≈ 可用端口数 ÷ TIME_WAIT 秒数 × 0.7；三个数字缺一不可：系统给了多少端口、关掉的连接占多久、单条连接平均活多久。**

前两个是系统参数，第三个由业务决定。为什么要打七折：端口分配不是完美均匀的，用掉八九成后冲突率陡增；系统自身和保留段要先吃掉一部分；业务连接耗时不是常数，赶上目标站慢，单条活得久、周转更慢。按七折估，实际能稳住的量级不会被高估。

| 业务形态 | 每秒新建连接 | 需占端口（×60 秒） | Linux 默认够不够 |
|---|---|---|---|
| 5 个后台窗口轮询 | 约 20 条 | 1,200 个 | 够，余量 96% |
| 50 并发采集 | 约 250 条 | 15,000 个 | 够，但只剩 47% |
| 200 并发短连接 | 约 600 条 | 36,000 个 | 不够，必报错 |
| 500 并发压测 | 约 1,500 条 | 90,000 个 | 差三倍以上 |

## 五种报错，五个位置

**报错原话里的关键词决定查哪里：带 assign、socket address、open files 的是本机资源；带 refused、reset、timeout 的才轮到线路。**

同样叫「连不上」，这五句指向的位置可能差着一台机器甚至一整条线路。客户端的绿灯只会说「未连接」，真正有用的是日志里的原话。

| 报错原话 | 环境 | 位置 | 先做什么 |
|---|---|---|---|
| Cannot assign requested address（errno 99） | Linux | 本机端口分配失败 | 看 TIME_WAIT 与端口范围 |
| Only one usage of each socket address（10048） | Windows | 端口被占用或落在保留段 | 查排除段 |
| buffer space / queue is full（10055） | Windows | 非分页池或句柄紧张 | 降并发、查句柄 |
| Too many open files | Linux | 文件句柄上限（默认 1024） | 调 ulimit -n |
| 全部超时、一个码都没有 | 任意 | 软路由 conntrack 满或上游 NAT | 看 conntrack 计数 |

Python 的 requests 会把 errno 99 包成「Max retries exceeded … Cannot assign requested address」。看到 Max retries 就去加重试，只会消耗得更快——重试本身也是新建连接。

## 四条命令，把情况看清

**Linux 上看 ss -s 的 timewait 计数、cat /proc/sys/net/ipv4/ip_local_port_range 的端口范围、ulimit -n 的句柄数；Windows 上用 netstat -ano 加 netsh int ipv4 show excludedportrange tcp 查保留段。**

四条命令的目的不是调参，是先确认到底哪一项撞了墙。端口范围还宽、timewait 只有几百、句柄也只用了三成，那就不是端口问题，别在这儿耗时间。

Windows 那台办公机实测过一组数：动态端口从 49152 起共 16,384 个，排除段里躺着 5357，当时 TIME_WAIT 117 条、ESTABLISHED 201 条——平时端口池几乎全空，撞墙只发生在并发真正打开的那几分钟。

## 三条解法，代价各不同

**优先复用连接，其次调参扩池，最后才是加出口；三者的成本差一个量级，效果却是前两条常常就够。**

复用连接（keep-alive / 连接池）是把「每条请求建一次连接」改成「一条连接跑多条请求」，端口占用直接降一到两个数量级，代价是服务端可能限制单连接请求数或超时。调参是扩池，Linux 把 ip_local_port_range 放宽、把 tcp_tw_reuse 打开，秒级上限能翻倍，代价是 TIME_WAIT 复用有极小概率踩到旧连接。加出口是加一条代理线路，让客户端从两个源地址出去，等于把一维变回两维，代价是月费。

| 解法 | 效果 | 代价 | 什么时候用 |
|---|---|---|---|
| 复用连接 | 端口占用降 1–2 个数量级 | 需要改代码 | 首选，尤其短连接密集的场景 |
| 调端口范围 / 复用 | 秒级上限约翻倍 | 需重启或改内核参数 | 复用做了还不够 |
| 加一条出口 | 上限按出口数倍增 | 月费 + 分流配置 | 并发确实大、代码改不动 |

## 什么情况不是端口问题

**报错里没有 assign、也没有 open files，且并发并不高，就别在端口上找原因——这类多数是线路侧限速、目标站限流或软路由连接表满。**

区分方法很朴素：把并发降到 5，还报同样的错，就不是资源耗尽；降到 5 就正常，才是资源耗尽。第二步看错误原话属于哪一类，第三步才看线路。

## 自测口径：三项，十分钟

**先降并发复测（5 并发是否正常）、再看 timewait 与端口范围、最后用同一条线在另一台机器上跑同一份脚本——三项能把「本机 / 线路 / 目标站」分开。**

第二项决定要不要调参，第三项决定要不要换线。同一份脚本换一台机器就正常，说明问题在原机器；换机器也一样，才轮到线路和目标站。

## 常见问题

**问：采集跑到一半全超时，是 IP 被封了吗？**
答：看报错原话。带 Cannot assign requested address 的是本机端口用完，不是被封；被封通常表现为连接被拒、被重置或直接超时。

**问：为什么加了带宽还是报同样的错？**
答：带宽是管子粗细，端口是号牌数量。号牌发完，管子再粗也进不去，加带宽对这处瓶颈无效。

**问：Linux 默认到底能撑多少并发？**
答：按 60 秒 TIME_WAIT 算，理论每秒 470 条新连接，实测打七折约 330 条。短连接采集在这个量级上就会开始零星报错。

**问：Windows 为什么比 Linux 更容易撞墙？**
答：默认端口少（16,384 对 28,232）、TIME_WAIT 还长一倍（120 秒对 60 秒），秒级上限只有 137 条。

**问：Too many open files 也是端口问题吗？**
答：不是，是文件句柄上限（默认 1024）。这一项要先调 ulimit -n，调完再看端口。

**问：加一条出口能解决吗？**
答：能，但成本最高。先做连接复用、再调端口范围，两条做完还不够，才考虑加出口。
