# 代理IP 认证填反了要花一整晚排查：白名单和账号密码，选错就在这一步

填错认证方式这一栏，付出的往往是一整晚的排查成本——线路本身没问题，是「认来源」和「认凭证」这两条路被弄反了。**代理IP 的身份验证只有两种：IP 白名单先把你当前的公网地址登记进后台，连接时不再带凭据；账号密码每次连接都要带上一组用户名加密码。** 连不上的第一排查项，永远是这两者有没有填反。

## 校验的对象根本不同：一个看来源，一个看凭证

IP 白名单的校验对象只有一样东西——你的来源地址。代理服务器收到连接后，先看这个请求从哪个公网地址发出、在不在你登记过的名单里，在就直接放行，整个连接过程不带任何用户名密码。它对应的是网络层最朴素的「信任来源」，所以快、省事，也最怕来源变化。

账号密码走的是另一条路。SOCKS5 在 RFC 1928 里定义了「用户名/密码认证」这一子协商方式（方法码 0x02，细节见 RFC 1929），HTTP 代理则用 Basic 认证（RFC 7617）把用户名和密码放在请求头里。两者的共同点是：**校验的是凭证，不是来源**。你从家里宽带连、从公司网络连、从手机热点连，只要凭证对，就能通。

把这一点想通，后面所有现象都能解释：白名单失效 = 来源变了；账密失效 = 凭证抄错了或者被改了。这两件事的排查方向完全相反，弄反了就会越修越乱。

## 两种认证摆在一起看

| 对比维度 | IP 白名单 | 账号密码 |
|---|---|---|
| 校验对象 | 来源公网地址 | 用户名 + 密码 |
| 出口地址变了 | 立即失效，需重新登记 | 不受影响 |
| 凭证泄露风险 | 低（本机根本没有密码） | 有，注意不要把参数外发 |
| 后台配置位置 | 「IP 白名单 / 免密登录」一类设置 | 提取时生成，或后台查看 |
| 典型工具 | 软路由、固定 IP 服务器、部分 SDK | 老鱼、SSTap、NekoBox、浏览器插件 |
| 常见故障 | 拨号换 IP、多设备共用一条出口 | 复制带空格、全角字符、大小写错 |

## 你这台机器的出口固不固定，决定了选哪个

选哪种认证，不取决于平台，取决于你这条线的出口稳不稳。判断方法很简单：把路由器断电重启一次，或者重新拨号一次，看公网地址有没有变——会变的就用账密，不变的才适合白名单。

| 使用环境 | 出口是否固定 | 推荐认证 |
|---|---|---|
| 云服务器 / 有固定公网地址的机器 | 固定 | 白名单 |
| 固定宽带 + 软路由 | 固定 | 白名单 |
| 家用宽带（PPPoE 拨号） | 会变 | 账号密码 |
| 手机热点 / 多设备轮换 | 会变 | 账号密码 |

## 昨天能连今天连不上，基本都出在出口变了

这是白名单最典型的一次故障，也最容易被误判成「线路挂了」。如果你的机器是拨号上网，运营商重新分配地址之后，后台登记的名单就对不上了，代理自然拒绝连接——但同一时刻换台设备用账密连，线路是好端端的。

所以排查顺序建议固定下来：先用站内的代理线路可用性检测做一次真实握手，确认地址和端口本身通得过去；再回头核对认证形式与当前工具是否一致。**握手通、认证不过，问题就在认证这一栏。** 站内 23 家合作平台的起步价从 2.24 元到 20 元/月不等，但无论买哪一档，这一步的排查逻辑是一样的。

另外提一句账密的常见坑：后台生成的用户名密码里可能夹带大小写混排，从网页复制到客户端时容易带上尾随空格或全角字符。这类问题的表现和白名单失效很像，但定位方式不同——把凭据重新完整复制一次即可排除。

## 常见问题

**Q：同一串地址，软路由里能连，换到浏览器插件就报认证失败，是什么原因？**
多数是认证形式对不上。软路由这类固定出口适合白名单，浏览器插件走的是每次带凭证的方式，如果你的后台只登记了白名单、没开账密通道，插件自然会失败。换一种入口，就可能要通过的方式不同。

**Q：怎么确认我现在的公网地址变没变？**
把路由器断电重启，或者手动重新拨号一次，再看当前的公网地址。变了就说明这条线是动态的，应该改用账号密码；不变才适合登记白名单。

**Q：白名单和账号密码能同时开吗？**
多数平台可以同时保留两种通道，但建议只留一种在用，另一种关掉。两套并存时，出问题要同时排查两个方向，反而更慢。

**Q：账号密码会不会更不安全？**
风险点是凭证外泄，而不是协议本身。SOCKS5 的用户名密码子协商和 HTTP Basic 都属常见实现，真正的纪律是不要把带凭证的参数随手贴到公开渠道。

**Q：多台设备共用一条出口，选哪种？**
建议用账号密码。多台设备共用意味着来源地址会随时变化，白名单需要反复登记，维护成本远高于账密。
