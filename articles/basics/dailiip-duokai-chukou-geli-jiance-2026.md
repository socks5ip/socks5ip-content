# 多开却没隔离：单窗口单 IP 到底卡在哪一步（2026）

多开 8 个模拟器窗口，第 4 个窗口开始频繁弹验证——8 条线路没少配，问题出在出口只挂了一个。这是多开场景里最常见的一种错觉：买了足够多的 IP，也按教程填进了软件，但所有窗口走的仍然是同一个出口。

## 挂了一个代理，为什么八路还是同一个出口

代理的生效范围决定了它管到哪一层。系统级设置只影响「走系统代理设置的那些程序」，而模拟器往往自带网络栈、或者直接走底层网卡，系统代理对它是透明的。

| 生效范围 | 管到谁 | 对模拟器多开的效果 |
|---|---|---|
| 系统代理 | 遵循系统代理设置的程序 | 浏览器类可用，模拟器常绕过 |
| 进程代理 | 指定进程名或路径的流量 | 需逐个指定，漏一个就串一路 |
| 驱动级代理 | 网卡层所有流量 | 覆盖完整，多开场景最稳 |

三种范围由上到下依次变深，隔离能力也依次变强。多开场景卡住，多数时候是停在了第一层。

## 隔离深度分三层：系统、进程与网卡

1. **系统代理**：在操作系统里填地址端口。优点是配置简单；缺点是只管听话的程序，模拟器、游戏客户端、内置下载器都可能不受管。
2. **进程代理**：按进程把流量分流到不同出口。问题在于要维护一份进程清单，多开时每个窗口都是同名的实例，靠进程名可能分不开。
3. **驱动级代理**：在网卡层拦截，按连接分配出口，不依赖程序是否配合。配合「一个窗口一个出口」的规则时最不容易漏。

## 单窗口单 IP 的配置顺序

顺序错了会在中途反复返工，按下面六步走：

1. 先把线路信息备齐：地址、端口、账号、密码、协议类型，一条一行。
2. 在代理软件里建立「线路池」，确认每条都能单独连通。
3. 设置分配规则：按窗口、按进程或按连接建立出口绑定关系。
4. 逐个启动窗口，每启动一个确认绑定到了预期的那条出口。
5. 全部启动后，逐个窗口查一次出口 IP，确认没有重复。
6. 最后再跑业务脚本。**先验出口，再跑业务**，这个顺序不能反。

## 串线的四个常见来源

| 现象 | 来源 | 处理 |
|---|---|---|
| 前几个窗口正常，后面的都同一个出口 | 线路池数量少于窗口数，超出部分回落到默认出口 | 补足线路或限制并发窗口数 |
| 全部窗口同一个出口 | 代理只对系统生效，模拟器没走代理 | 改为进程代理或驱动级代理 |
| 偶尔串线，重启后正常 | 分配规则按启动顺序轮询，重启打乱了对应关系 | 改为固定绑定而非轮询 |
| 业务脚本报错时串线 | 脚本自身的网络请求没走代理通道 | 在脚本层显式指定出口 |

第三和第四条最容易被误判成「线路质量差」，实际与线路无关。

## 验证隔离有没有真正生效

不看软件界面上的状态，只看结果：

- **逐窗查出口**：每个窗口访问同一个出口检测页，记录返回的 IP。
- **比对去重**：把记录下来的 IP 去重，数量应等于窗口数。
- **反复抽查两轮**：间隔几分钟再查一次，确认绑定没有漂移。

三项都通过，才说明隔离真的生效。只要有一项没过，先按上一节的来源表排查，不要急着换线路。

## 常见问题

**Q：软件里显示已连接，就说明隔离生效了吗？**
A：不能这么判断。界面显示的是软件与代理服务器之间的连接状态，不是每个窗口的实际出口。要逐窗查出口 IP 才算数。

**Q：线路数量必须大于窗口数吗？**
A：峰值时同时运行的窗口数不能超过可用线路数，否则超出的部分会回落到默认出口，表现就是「后面几个窗口串线」。

**Q：用哪种协议对隔离效果有影响吗？**
A：有影响但排在第二位。隔离效果主要由代理的生效范围决定，协议选择更多影响兼容性与速度。

**Q：为什么重启软件后绑定关系就乱了？**
A：多半是分配规则按启动顺序轮询，而不是固定绑定。改成固定绑定后重启就不会错位。

**Q：多个窗口用同一台机器的不同网卡，能实现隔离吗？**
A：可以在物理链路上分开，但出口 IP 还是取决于各自走的代理，仍然要按上面的顺序逐窗验证。
